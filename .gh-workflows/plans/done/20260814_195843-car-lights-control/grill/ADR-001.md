# ADR-001: Binary Command Frame Format for TCP:100 Protocol

**Status:** Accepted

## Context

This plan adds LED light control to the existing ACEBOTT QD001 Electron app. Future plans will add other device controls (movement, buzzer, servo, etc.) that will also communicate with the car over the TCP:100 binary protocol. All of these will need to build and send command frames in the same wire format.

During the grill interview, the exact binary frame format was reconstructed from the ACEBOTT firmware source code (from `7_4APP_control_car.ino`'s `RXpack_func()` and `parseData()` functions, and the byte-identical parsing logic in the Python example at `7.4APPControlCar.py`). This ADR documents that format as the canonical reference for all future work that uses the TCP:100 protocol.

The format has never been live-tested against the user's actual QD001 car — it was reverse-engineered from firmware source code alone. A working implementation (this plan's implementation phase) will serve as the first live confirmation that the format is correct.

## Decision

All binary command frames sent over the TCP:100 protocol will follow this format:

### Frame Structure

```
Byte 0:      0xFF              (header byte 1)
Byte 1:      0x55              (header byte 2)
Byte 2:      <length>          (payload length in bytes, typically 0x0A for 10 bytes)
Bytes 3-12:  <payload>         (exactly <length> bytes of payload data)
```

### Payload Layout (10-byte payload, indices relative to byte 3)

```
Payload[0-2]:   (zeros or data, unvalidated by parser)
Payload[3-5]:   (zeros or data, unvalidated by parser)
Payload[6]:     <action>        (byte 9 of frame; command action: 0x01=CMD_RUN, 0x02=CMD_GET, etc.)
Payload[7]:     <device>        (byte 10 of frame; device code: 0x05=LED, 0x01=motor, etc.)
Payload[8]:     (reserved/padding, written but never read)
Payload[9]:     <value>         (byte 12 of frame; device-specific value: for LED, 0x00=off, 0x01=on)
```

### Example: LED On

To turn the LED on, send:
- Frame: `0xFF 0x55 0x0A 00 00 00 00 00 00 01 05 00 01`
- Breakdown:
  - `0xFF 0x55`: header
  - `0x0A`: payload length (10 bytes)
  - `00 00 00 00 00 00`: bytes [0-2] and [3-5], unvalidated
  - `01`: action (CMD_RUN)
  - `05`: device (LED)
  - `00`: padding
  - `01`: value (on)

### Example: LED Off

- Frame: `0xFF 0x55 0x0A 00 00 00 00 00 00 01 05 00 00`
- Same as above except last byte is `00` (off)

## Rationale

This frame format is:

1. **Documented in multiple firmware variants**: Appears identically in QD001 (`7_4APP_control_car.ino`) and QD005 (`acebott-esp32-car-shoot-005.ino` and `acebott-esp32-car-body.ino`) example firmware, suggesting it is the canonical ACEBOTT protocol, not a one-off implementation.

2. **Confirmed in actual running hardware**: The user's physical QD001 car (flash dump analyzed via `tools/qd001-probe/`) contains the same protocol parser strings and firmware version markers as the `7_4APP_control_car.ino` example, providing high confidence that the format applies to real hardware.

3. **Extensible for future work**: The same frame structure will carry movement commands (`device = 0x01`), buzzer commands, servo angles, etc. Documenting it once here avoids rediscovery and rework in future plans.

4. **Alignment with previous plan's architecture**: The previous `acebott-control-app` plan established that the main process owns all socket I/O (ADR-002 in that plan). This frame format is the wire contract for that I/O layer.

## Consequences

- **Implementation commitment**: The app will implement a function (or module) to construct frames in this exact byte order and send them over the TCP socket. Unit tests will verify correct frame construction for each device/action/value combination.

- **Live verification pending**: The format was reverse-engineered from source code, not tested against real hardware yet. The implementation phase must confirm that sending these frames actually commands the car's LEDs as expected. If the compiled firmware on the real car differs from the source (see facts 4 in requirements.md — the dump shows camera strings not in the example source), frame construction may need adjustment.

- **Reserved bytes**: The 7 unvalidated bytes in the frame (payload[0-2], payload[3-5], and payload[8]) can be safely zero-filled for now, but if future work discovers they carry meaning in the actual compiled firmware, they may need to be set to specific values. The frame is defensively structured to allow for this discovery without breaking the protocol.

- **No state feedback**: The protocol is one-directional (app sends frame, car processes it, no response). This limitation is accepted per the design decisions in this plan (see Decision 3: app-tracked state).
