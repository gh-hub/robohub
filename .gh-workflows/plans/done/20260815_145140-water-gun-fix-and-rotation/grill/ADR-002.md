# ADR-002: Discrete 90°/180° Rotate Buttons via Timed Pulse

## Status
Accepted

## Context

The app currently supports continuous hold-to-rotate D-pad buttons (`#rotate-left` and `#rotate-right`), which send a movement command continuously while held and stop when released. Users have requested one-click discrete rotation buttons for fixed angles (90° or 180°, left or right) without having to hold down a button.

The ACEBOTT QD005 firmware protocol has no angle-based rotation primitive — only `MOVEMENT_VALUES["rotate-left"]: 0x09` and `MOVEMENT_VALUES["rotate-right"]: 0x0a`, which spin the car continuously until a Stop command is sent. The only way to approximate a fixed angle turn from the app side is via a timed pulse: send the rotate command, wait a fixed duration, then send Stop. Actual angle accuracy depends on motor speed, battery voltage, and friction — variables that can only be calibrated against real hardware, not derived analytically.

## Decision

Add four new one-click rotation buttons: "Rotate 90° Left", "Rotate 90° Right", "Rotate 180° Left", "Rotate 180° Right". Each button:
1. Interrupts any currently-active D-pad hold (clears `activeDirection` in `app/src/renderer.ts`)
2. Sends the existing `rotate-left` (0x09) or `rotate-right` (0x0a) movement command via the TCP:100 protocol
3. Waits a fixed duration before sending Stop
4. Disables all movement and rotation buttons (both discrete and continuous) during the timed window, following the existing Shoot-cooldown pattern

### Concrete Implementation Details

**New constants in `app/src/renderer.ts`:**
```javascript
// UNVERIFIED durations pending hardware calibration — if rotation angle is off, tune these.
// See AIM_ANGLE_DELTA commentary for precedent.
const ROTATE_90_MS = 400;  // Duration to spin for approximately 90°
const ROTATE_180_MS = 800; // Duration to spin for approximately 180°
```

**New button HTML ids in `app/public/index.html`:**
- `#rotate-90-left-button`
- `#rotate-90-right-button`
- `#rotate-180-left-button`
- `#rotate-180-right-button`

(Distinct from existing `#rotate-left` and `#rotate-right` continuous D-pad buttons; recommend placing in a new `.dpad-discrete-rotate-row` section below `.dpad-rotate-row` or similar.)

**New handler in `app/src/renderer.ts`:**
```javascript
async function handleDiscreteRotate(direction: "left" | "right", angleDegrees: 90 | 180) {
  // Interrupt any active D-pad hold
  stopActiveMovement();
  
  // Disable all movement/rotation buttons
  const durationMs = angleDegrees === 90 ? ROTATE_90_MS : ROTATE_180_MS;
  setRotateCooldownActive(true);
  
  // Send rotate command
  const cmd = direction === "left" ? MOVEMENT_VALUES["rotate-left"] : MOVEMENT_VALUES["rotate-right"];
  sendMovementCommand(cmd);
  
  // Wait then send Stop
  await delay(durationMs);
  sendMovementCommand(MOVEMENT_STOP);
  
  setRotateCooldownActive(false);
}
```

(Or similar structure, depending on how the existing code is organized — key requirement is the interrupt + disable + timed pulse + reenable pattern.)

**New button event listeners in `app/src/renderer.ts`:**
- `#rotate-90-left-button` → `handleDiscreteRotate("left", 90)`
- `#rotate-90-right-button` → `handleDiscreteRotate("right", 90)`
- `#rotate-180-left-button` → `handleDiscreteRotate("left", 180)`
- `#rotate-180-right-button` → `handleDiscreteRotate("right", 180)`

**Disable/enable gating during cooldown:**
- Disable all movement buttons + discrete rotate buttons + continuous `#rotate-left`/`#rotate-right` buttons when `rotateCooldownActive` is true
- Enable them when `rotateCooldownActive` is false
- (Mirror the existing pattern used for Shoot cooldown: `shootCooldownActive` and `startShootCooldown()` in `renderer.ts`.)

## Why This Decision

The firmware protocol has no angle-based rotation primitive, only spin-until-stop. A timed pulse is the only implementation path available without firmware changes. The app-side timings are approximate and will need real hardware tuning; this is acceptable because the alternative (firmware modification) is out of scope. The constants are explicitly flagged as unverified placeholders to make clear that post-ship calibration is expected.

## Alternatives Rejected

**Add a firmware-side "rotate by N degrees" command:** Rejected as out of scope. This plan does not modify or reflash the ACEBOTT ESP32 firmware. The `.ino` sources in `docs/` are reference material only, not part of this repo's build/deploy pipeline. Firmware changes would require coordination with the hardware team and a separate release cycle.

**Use a different timing strategy (e.g., accelerometer-based):** Rejected because the QD005 build does not expose accelerometer data over the TCP:100 protocol (verified via `docs/qd001-hardware-access/protocol-reference.md`). A simple timed pulse is the only available mechanism.
