# Decisions: water-gun-fix-and-rotation

## Decision: Firmware/pin match confirmed
Decided: The physical car runs the stock ACEBOTT QD005 firmware. GPIO 26 (`TURN_SERVO_PIN`) is the hardware the app's `DEVICE_SERVO = 0x02` command targets — no "pin 4" servo or alternate servo channel exists in any variant of the QD005 firmware. No firmware-pin code changes needed in `app/src/`.
Why: Verified directly against the actual `.ino` sketches (Car A and Car B variants) found in `docs/ACEBOTT QD005 Shooting Car V1 Tutorial V2.9/Arduino(Experienced Learner)/ACEBOTT QD005 ESP32 Shooting Car A/2.Program file/` rather than guessing from documentation; user confirmed this matches their physical unit.
Alternatives rejected: None — this was a factual verification, not a design choice.

## Decision: Repurpose Aim Up/Down into Pan Left/Right
Decided: The single controllable servo (GPIO 26 / device `0x02`) is physically mounted on this build to pan the ultrasonic distance sensor bracket left/right, not to aim the gun barrel up/down. Repurpose the existing Aim control end-to-end rather than adding a new one: rename `AimDirection` from `"up"|"down"` to `"left"|"right"`, rename all associated identifiers/labels (`aim-up-button`/`aim-down-button` → `pan-left-button`/`pan-right-button`, "Aim: 90°" → "Pan: 90°", `mapAimControlUiState`'s `upDisabled`/`downDisabled` → `leftDisabled`/`rightDisabled`). Keep all underlying mechanics unchanged: same `DEVICE_SERVO` angle-step-and-send logic, same 1–180° bounds, same Fast(10°)/Slow(5°) step dropdown, same press-and-hold repeat timer (400ms), same connection gating.
Why: There is no second servo/device-code available in the protocol to add a "real" gun-aim axis — the existing control is the only reachable servo, so relabeling it to match its actual physical behavior (panning, left/right) is the correct fix, not adding new hardware capability that doesn't exist. Confirmed via `docs/qd001-hardware-access/protocol-reference.md`'s full device-code table: only `0x02` is a servo channel.
Alternatives rejected: Adding a brand-new "true aim" control — rejected because no second servo channel exists in the firmware's protocol.

## Decision: Shoot diagnosed as a hardware issue, not a code bug
Decided: The app's `DEVICE_SHOOT = 0x08` command already matches the firmware's expected pulse byte-for-byte (confirmed via the actual `.ino` source), and the UI gating logic (`mapShootControlUiState`) was independently re-verified as correct. Clicking Shoot produces zero physical effect because of a hardware-layer problem (wiring, the blaster motor/pump itself, or the unidentified `U4` driver chip near the "Shoot" JST connector on the QA052 shield — documented in `docs/qd001-hardware-access/pin-mapping.md`'s "Unidentified" note). No code fix exists here; document the diagnosis and provide troubleshooting guidance.
Why: The protocol-level command already matches firmware source exactly; there is nothing left to change in software. This is a physical hardware repair task for the user, not a code task.
Alternatives rejected: Speculatively changing the shoot pulse shape/timing (e.g., different pulse width, PWM instead of digital) — rejected because the firmware source shows no such variant exists to try; guessing at pulse changes without hardware access would be unverifiable and not grounded in evidence.

## Decision: Add 4 new discrete rotate buttons
Decided: Add "Rotate 90° Left", "Rotate 90° Right", "Rotate 180° Left", "Rotate 180° Right" as new, separate one-click buttons (distinct from the existing continuous hold-to-rotate `#rotate-left`/`#rotate-right` D-pad buttons, which stay as-is). Each button's click handler: interrupt any currently-active D-pad hold (overwrite/clear `activeDirection`), send the existing `rotate-left`/`rotate-right` movement command (protocol values `0x09`/`0x0a` already defined in `MOVEMENT_VALUES` — no new device/protocol code needed), wait a fixed duration, then send Stop. During that timed window, all movement + rotate buttons (both discrete and continuous) are disabled, mirroring the existing Shoot-cooldown disable-during-action pattern in `renderer.ts` (`shootCooldownActive`/`startShootCooldown()`). Default placeholder durations: `ROTATE_90_MS = 400`, `ROTATE_180_MS = 800` — explicitly flagged in a code comment as unverified/pending hardware calibration, following the exact same commenting precedent already used for `AIM_ANGLE_DELTA` in the prior plan.
Why: The firmware protocol has no angle-based rotation primitive — only "spin continuously until Stop is sent" (confirmed via `docs/qd001-hardware-access/protocol-reference.md`'s full device/action-code table). A timed pulse is the only way to approximate a fixed-angle turn from the app side; real accuracy depends on motor speed/battery/friction and can only be tuned against the physical hardware, not derived analytically.
Alternatives rejected: A firmware-side "rotate by N degrees" command — rejected as out of scope; this plan does not modify or reflash firmware (docs/ firmware sources are reference-only, not part of this repo's build/deploy pipeline).
