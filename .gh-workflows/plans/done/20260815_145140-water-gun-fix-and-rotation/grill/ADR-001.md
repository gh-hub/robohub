# ADR-001: Repurpose Aim Up/Down into Pan Left/Right

## Status
Accepted

## Context

The ACEBOTT QD005 water-gun build has a single controllable servo (GPIO 26 / device code `0x02`), which is physically mounted on this unit to pan the ultrasonic distance sensor bracket left and right — not to aim the gun barrel up and down. The app currently labels this control "Aim Up/Down", which is semantically incorrect and confusing to the user.

The protocol supports only one servo channel (`0x02`), confirmed by reading the full device-code table in `docs/qd001-hardware-access/protocol-reference.md` and the actual QD005 firmware `.ino` sketches (Car A and Car B variants). No second servo for a "real" gun-aim axis exists or is reachable via the wire protocol.

## Decision

Repurpose the existing Aim control end-to-end as Pan, renaming all labels, identifiers, and type names from up/down semantics to left/right semantics, while keeping the underlying protocol mechanics completely unchanged.

### Concrete Scope of Changes

**Type and variable renames in `app/src/renderer.ts`:**
- `AimDirection` type: `"up" | "down"` → `"left" | "right"`
- `AIM_ANGLE_DELTA` → `PAN_ANGLE_DELTA`
- `AIM_BUTTON_IDS` → `PAN_BUTTON_IDS`
- `aimAngle` state var → `panAngle`
- `aimSpeed` state var → `panSpeed`
- `aimHoldDirection` state var → `panHoldDirection`
- `aimRepeatTimer` state var → `panRepeatTimer`
- `AIM_REPEAT_INTERVAL_MS` → `PAN_REPEAT_INTERVAL_MS` (value unchanged: 400ms)
- `AIM_STEP_DEGREES` → `PAN_STEP_DEGREES` (structure unchanged: `{fast: 10, slow: 5}`)
- `MIN_AIM_ANGLE` / `MAX_AIM_ANGLE` → `MIN_PAN_ANGLE` / `MAX_PAN_ANGLE` (values unchanged: 1/180)
- Function renames: `stepAim()` → `stepPan()`, `handleAimPointerDown()` → `handlePanPointerDown()`, `handleAimRelease()` → `handlePanRelease()`, `renderAim()` → `renderPan()`

**Function signature updates (in `app/src/connectionUiState.ts`):**
- `mapAimControlUiState()` → `mapPanControlUiState()`
- Function body field names: `upDisabled` / `downDisabled` → `leftDisabled` / `rightDisabled`

**UI label and button id renames (in `app/src/renderer.ts` and `app/public/index.html`):**
- HTML element id renames: `#aim-up-button` → `#pan-left-button`, `#aim-down-button` → `#pan-right-button`
- Label text: "Aim: 90°" → "Pan: 90°"
- HTML div id: `#aim-controls` may optionally be renamed to `#pan-controls` (consistency, not required)

### Unchanged Mechanics

All of the following remain exactly the same, with no behavioral changes:
- **Protocol command:** Still `DEVICE_SERVO = 0x02` (from `app/src/commandFrame.ts`)
- **Angle bounds:** Still 1–180°
- **Step sizes:** Still Fast (10°) / Slow (5°)
- **Press-and-hold repeat:** Still 400ms interval
- **Connection gating:** Still `connection.status !== "connected" || connection.protocol !== "tcp100"` (from `mapPanControlUiState()`)
- **Step direction logic:** If the direction sign is incorrect (e.g., left moves right instead), the single-line toggle is `PAN_ANGLE_DELTA` — same precedent as `AIM_ANGLE_DELTA` in the prior plan.

## Why This Decision

The existing servo is the only reachable one in the protocol. Correctly labeling it as "Pan" instead of "Aim" removes semantic confusion and aligns the UI with the actual physical hardware behavior. No new hardware capability is introduced; only naming and semantics change to match reality.

## Alternatives Rejected

**Add a brand-new "true aim" servo control:** Rejected because no second servo channel exists in the firmware's protocol. The full device-code table in `docs/qd001-hardware-access/protocol-reference.md` shows only `0x02` as a servo channel. Adding a control for non-existent hardware would be dead code.
