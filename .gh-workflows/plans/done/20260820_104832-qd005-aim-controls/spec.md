## Problem Statement

The QD005 water-gun attachment's aim servo (GPIO 26, device code `0x02`) physically moves the gun barrel up and down. But the app labels this control "Pan Left/Right" everywhere — in code identifiers, IPC channel names, comments, and the on-screen UI (buttons read "◀ Left" / "▶ Right", the readout says "Pan: 90°"). That name is a leftover from an earlier, mistaken assumption about the servo's motion, and it now actively misleads anyone reading the code or using the app: the control moves the gun vertically, not horizontally.

Separately, the QD005's two controls — the aim servo and the shoot/blaster trigger (device code `0x08`) — currently render as two plain, undifferentiated `<div>`s sitting in the page flow alongside the car's own Movement and Lights controls. Nothing in the UI signals that these two controls belong together as "the water-gun attachment," as distinct from the car's native controls.

## Solution

Rename the control from "Pan Left/Right" to "Aim Up/Down" consistently across every layer of the app — protocol comments, the UI-state mapper, the IPC channel and preload bridge, main-process wiring, the IPC handler and its validation, the connection class, the renderer's DOM/state logic, and the HTML markup/CSS/labels/button glyphs — plus every corresponding test file. This is a pure identifier and label rename: the wire protocol, frame bytes, angle bounds (1–180, integer), gating/rejection behavior, and step/speed behavior are all unchanged.

The direction sign is set as an explicit, flagged-as-unverified placeholder: Up increases the angle toward 180°, Down decreases it toward 1°. This mirrors how the prior "Pan" implementation flagged its own direction-sign constant, and remains a single easy-to-flip constant once real hardware calibration confirms (or corrects) the mapping.

Additionally, introduce a new boxed "QD005 Water Gun" section in the UI that visually groups the (renamed) Aim controls with the existing Shoot controls, styled after the app's existing `.log-panel-container` boxed pattern (bordered box with a heading). The section occupies the exact same page position the two flat divs occupy today — after `#movement-controls`, before `#log-panels` — so no other part of the page reorders. Aim's Up/Down buttons switch from the old ◀/▶ glyphs to ▲/▼ (`&#9650;`/`&#9660;`), matching the D-pad's forward/backward glyph convention.

## User Stories

1. As a developer reading `commandFrame.ts`, `carConnection.ts`, or `carIpcHandlers.ts`, I want the device-0x02 servo referred to as the "aim servo" everywhere, so that the code accurately describes what the hardware does and doesn't perpetuate the incorrect "pan" assumption.
2. As a developer working on `connectionUiState.ts` or `renderer.ts`, I want the UI-state types, constants, and functions named for "Aim"/"Up"/"Down" (not "Pan"/"Left"/"Right"), so that identifier names match the semantics they represent.
3. As a developer extending the IPC surface, I want the channel constant, preload bridge method, and main-process handler all named `...AimAngle...` consistently, so there's a single unambiguous name for this control across the process boundary.
4. As a user operating the app, I want to see "Aim Up" / "Aim Down" buttons with up/down triangle glyphs (not left/right arrows), so the on-screen control matches the gun's actual vertical motion.
5. As a user operating the app, I want the angle readout to say "Aim: 90°" (not "Pan: 90°"), so the label matches the control's real name.
6. As a user operating the app, I want the Aim and Shoot controls visually grouped in a single labeled "QD005 Water Gun" box, so I can immediately see which controls belong to the water-gun attachment versus the car's own Movement/Lights controls.
7. As a user operating the app, I want the QD005 Water Gun section to appear in the same place on the page it does today (right after the movement controls), so my existing muscle memory for where to find these controls isn't disrupted.
8. As a developer maintaining the test suite, I want every existing test file that references "Pan"/"pan"/"PAN" identifiers (`connectionUiState.test.ts`, `carIpcHandlers.test.ts`, `carConnection.test.ts`) updated in lockstep to the "Aim" equivalents, so test coverage is preserved exactly (same assertions, same bound cases) under the new names.
9. As a developer calibrating the servo against real hardware later, I want the direction-sign mapping (`Up → +1 delta`, `Down → -1 delta`) isolated to a single constant with a clear "unverified" comment, so flipping the sign after calibration is a one-line change.

## Implementation Decisions

- **Scope of the rename**: purely identifiers, labels, comments, DOM ids, and CSS selectors. No change to: the binary command-frame protocol, `DEVICE_SERVO = 0x02`, frame byte layout, angle bounds (1–180 integer), speed/step values (Fast/Slow), hold-repeat interval, connection-gating logic, or reset-to-90°-on-connect/disconnect/error behavior. Every renamed function/method keeps its existing body logic untouched except for internal references to renamed constants/types.
- **Layers touched** (per the Environment notes' full identifier inventory — already confirmed, not re-verified here): `commandFrame.ts` (doc comment only), `connectionUiState.ts` + its test, `ipcChannels.ts`, `preload.ts`, `main.ts`, `carIpcHandlers.ts` + its test, `carConnection.ts` + its test, `renderer.ts`, `index.html`.
- **IPC channel string value**: per the prior water-gun-fix-and-rotation precedent (ADR-001's sibling ticket), the channel string itself (not just the TypeScript identifier) is renamed — `"car:set-pan-angle"` → `"car:set-aim-angle"`. This channel has no external or persisted consumers (purely an internal main↔renderer IPC label), so there's no compatibility concern in renaming the wire string alongside the identifier.
- **Direction-sign constant**: the delta-map (`{ up: 1, down: -1 }`, replacing `{ left: 1, right: -1 }`) keeps the same numeric values as before, just remapped to the new key names — Up correlates to the same `+1` delta the old "Left" did. The accompanying code comment must explicitly flag this mapping as unverified pending physical hardware calibration, mirroring the prior Pan implementation's own flagged constant.
- **New "QD005 Water Gun" section**: a new semantic `<section>` (or `<div>`, matching how `#movement-controls`/`#light-controls` are currently plain divs — use judgment for semantic-HTML correctness, `<section>` is preferred since it has a heading) with an `<h2>` (or similar) titled "QD005 Water Gun", replacing the current flat `#pan-controls` and `#shoot-controls` divs at that page position with one wrapping container. The renamed Aim controls and the existing (logic-untouched) Shoot controls both move inside this new wrapper. New CSS class (e.g. `.qd005-section`) modeled on `.log-panel-container` (border, border-radius, padding, heading spacing) — not a byte-for-byte copy, since `.log-panel-container` is a flex-item sizing class for a multi-column log layout and this is a single standalone section; borrow the border/heading visual treatment, not the flex-sizing rules.
- **Shoot controls**: only their container/wrapping changes (they move inside the new QD005 section); `#shoot-button`, `#shoot-cooldown-toggle-label`/`#shoot-cooldown-toggle` ids, and all associated renderer.ts wiring/logic are untouched.
- **Button glyphs**: Aim Up uses `&#9650;` (▲), Aim Down uses `&#9660;` (▼) — reusing the exact D-pad forward/backward glyphs, replacing the old `&#9664;`/`&#9654;` (◀/▶).
- **No expand-contract**: per the grill decision, this is a single-app codebase (not a shared library with external consumers) and the prior water-gun-fix-and-rotation plan set precedent for doing this exact class of rename as one atomic batch across all layers, rather than splitting into expand/contract phases. The same approach applies here.

## Testing Decisions

- **Existing seams, renamed in place**: this repo has unit-test coverage for `connectionUiState.ts`, `carIpcHandlers.ts`, and `carConnection.ts`. Each of those tests is renamed in lockstep with its production code — same test cases, same bound assertions (e.g. the angle-bound test suite currently asserting `leftDisabled`/`rightDisabled` gets renamed to assert `upDisabled`/`downDisabled` with the bound semantics preserved 1:1, not flipped), same coverage, just new names (`VALID_PAN_ANGLES`/`INVALID_PAN_ANGLES` → `VALID_AIM_ANGLES`/`INVALID_AIM_ANGLES`, `/Invalid pan angle/` → `/Invalid aim angle/`, etc.).
- **No new test seam for the UI grouping**: this codebase has no DOM/UI test harness for `index.html`/`renderer.ts` (confirmed in requirements.md's Environment notes, consistent with how the prior "water-gun-fix-and-rotation" and "water-gun-control" plans handled `renderer.ts`/HTML changes). The new "QD005 Water Gun" boxed section and the `renderer.ts` DOM-wiring changes are verified only via `npm run build` / `npm run typecheck` passing cleanly, plus manual/visual inspection where the app/hardware is available. No new test infrastructure is introduced by this plan.
- **Full acceptance bar**: `npm test`, `npm run typecheck`, and `npm run build` all pass cleanly inside `app/`, with zero leftover `pan`/`Pan`/`PAN` references anywhere in `app/src/` or `app/public/index.html` (verifiable via a full-text grep across the touched files, as the prior rename ticket did).

## Out of Scope

- No new protocol/device codes, no wire-format changes, no change to `DEVICE_SERVO = 0x02` or the shoot trigger's `0x08` device code.
- No changes to Movement/Lights/Shoot *behavior* — Shoot's container is regrouped but its logic/handlers/ids are untouched.
- No touching the firmware's internal GPIO 25 servo (`fixedServo`, the base QD001 car's distance-sensor pan servo). This servo has no protocol device code and is currently driven only internally by the firmware's obstacle-avoidance logic — it is not reachable from the app at all. During the interview, the user separately raised wanting left/right control of this different servo; the user and the session agreed this is explicitly out of scope for this plan since it is not part of QD005, and would require firmware changes plus physical reflashing — a separate undertaking. A new, separate plan will be started for it later.
- No verifying the true physical up/down direction against real hardware — the placeholder direction sign (Up→180°, Down→1°) is accepted as-is; calibration is deferred.
- No new DOM/UI test harness or automated visual regression tooling — out of scope for this plan, consistent with the codebase's existing testing posture for `renderer.ts`/`index.html`.
