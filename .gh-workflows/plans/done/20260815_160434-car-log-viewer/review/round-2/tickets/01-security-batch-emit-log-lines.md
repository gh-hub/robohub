# 01 — [security] Batch log-line emission per chunk instead of one IPC send per line

**What to build:** `LogLineBuffer.push()` can return many lines from a single chunk of socket/serial data (e.g. a chunk consisting mostly of newline bytes can yield tens of thousands of lines from one `push()` call). Currently both `app/src/carConnection.ts` (tcp100 socket `data` handler) and `app/src/usbSerialConnection.ts` (USB serial `data` handler) loop over every returned line and call `this.emit("log-line", line)` once per line — each of which triggers a separate synchronous IPC `webContents.send` in the main process and a separate `appendLogLines`/`renderLogPanel` DOM reflow in the renderer. A chunk with many newlines (from the car firmware misbehaving, or — since the tcp100 socket is unauthenticated/unencrypted — a LAN attacker spoofing/MITM-ing the car's TCP endpoint) can therefore stall the single-threaded Electron main process and freeze the renderer via tens of thousands of back-to-back IPC sends and reflows in one synchronous burst. Fix this by emitting all lines produced by a single `push()` call as one batch (e.g. `this.emit("log-lines", lines)` with an array, or equivalent) instead of one event per line, and update the IPC forwarding (`carIpcHandlers.ts`'s `forwardWifiLogLines`, `usbLogIpcHandlers.ts`'s equivalent) and the renderer's subscription handlers to receive and append a batch of lines in a single IPC message and a single DOM update, reusing `appendLogLines`'s existing support for appending multiple lines at once (check `app/src/logPanel.ts` — `appendLogLines` already accepts an array of new lines per its existing tests). This eliminates the per-line IPC/DOM overhead entirely rather than dropping or rate-limiting legitimate log data.

**Blocked by:** None — can start immediately.

- [x] A single `push()` call's worth of lines (however many) is emitted as one batch/array event, not one event per line — both `carConnection.ts` and `usbSerialConnection.ts` now emit `this.emit("log-lines", lines)` once per `data` chunk (skipped entirely when `lines.length === 0`, i.e. a chunk with no complete line yet)
- [x] `carConnection.ts`'s tcp100 log-line forwarding and `usbSerialConnection.ts`'s USB log-line forwarding both use the new batched emission
- [x] The IPC forwarding functions (`forwardWifiLogLines` and the USB equivalent in `usbLogIpcHandlers.ts`) forward the batch as a single IPC message — both now listen for `"log-lines"` and pass the array straight through to `sendLines`/`webContents.send` in one call
- [x] The renderer receives and appends a batch of lines via a single call into `appendLogLines`/`renderLogPanel` (one DOM update per chunk of incoming data, not one per line) — `renderer.ts`'s `onWifiLogLines`/`onUsbLogLines` handlers now call `appendLogLines(existing, lines)` once per batch, followed by one `renderWifiLog()`/`renderUsbLog()` call
- [x] A test proves a chunk producing many lines (e.g. a chunk that is mostly `\n` bytes) results in exactly one emitted event/one IPC send/one renderer append call carrying all those lines, not one per line — new tests in `carConnection.test.ts` and `usbSerialConnection.test.ts` (`"a chunk producing thousands of lines still emits exactly one \"log-lines\" event carrying all of them"`, 20,000-line chunk); `forwardWifiLogLines`/`forwardUsbLogLines` tests already prove the IPC-forwarding side stays 1:1 with the emitted event; the renderer's DOM-wiring layer (`renderLogPanel`) is manual-testing-only per spec.md's existing Testing Decisions, unchanged by this fix
- [x] Existing tests for `CarConnection`'s `"log-line"` behavior, `UsbSerialConnection`'s log emission, `carIpcHandlers.test.ts`'s forwarding tests, and `usbLogIpcHandlers.test.ts`'s forwarding tests are updated to match the new batched shape
