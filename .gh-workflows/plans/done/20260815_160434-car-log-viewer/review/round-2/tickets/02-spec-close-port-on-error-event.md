# 02 — [spec] Close the USB serial port when an "error" event fires, not just on explicit Disconnect

**What to build:** Per spec.md user story 7, the serial port must be "cleanly closed when I click the USB Log Disconnect button or when I close the app, so that other tools can use the port immediately afterward, with no lingering lock." Currently, in `UsbSerialConnection.attachSessionListeners()` (`app/src/usbSerialConnection.ts:200-202`), a non-closing `"error"` event on the underlying port (e.g. a failed write, a device fault short of a full disconnect) sets the connection's status to `"error"` but never calls `port.close()` and never clears the internal port reference. After that happens: `disconnect()` rejects synchronously because the state is no longer `"connected"`, and `main.ts`'s `before-quit` cleanup handler (`main.ts:62-66`) only calls `disconnect()` when `status === "connected"` — so neither path can close the now-orphaned port. A subsequent `connect()` call opens a brand-new port without ever closing the stale handle, and the OS-level serial handle can remain open/locked indefinitely with no remaining code path to release it. Fix this so that when the underlying port emits `"error"`, `UsbSerialConnection` also closes the port (best-effort — the close itself may fail, which is fine) and clears its internal port reference, so no handle is ever left open after an error, and a subsequent `connect()` always starts from a clean slate. Consider whether `main.ts`'s `before-quit` handler also needs to account for the `"error"` state (it currently only checks for `"connected"`) to ensure app-close cleanup is thorough regardless of which state the connection was in.

**Blocked by:** None — can start immediately.

- [x] When the underlying serial port emits `"error"`, `UsbSerialConnection` closes the port and clears its internal port reference (best-effort close; a close failure doesn't throw uncaught) — `attachSessionListeners()`'s `"error"` handler (`usbSerialConnection.ts`) now sets error state, nulls `this.port` synchronously, then calls `port.close()` inside a `try/catch` that swallows a close failure.
- [x] After an `"error"` event, calling `connect()` again works cleanly and does not leave two port handles open — the `"close"`/`"error"` listeners now guard on `this.port !== port` (stale-listener check) so a delayed `"close"` from the best-effort close above can never null out or clobber a subsequently opened port's reference/state. Verified by a race-shaped test that lets the errored port's queued `"close"` microtask actually fire after a second `connect()` has already succeeded.
- [x] `main.ts`'s `before-quit` cleanup reliably releases the port regardless of whether the connection was in `"connected"` or `"error"` state at shutdown — considered and left as `status === "connected"` only, with a new comment explaining why: `UsbSerialConnection`'s port-field invariant (also newly documented) guarantees `this.port` is already null whenever status is `"error"`, since the fix above closes it at the source. No reachable "error"-with-a-live-handle state remains, so no `before-quit` change was needed (avoids an unwanted fallback branch per the "no scenario that cannot happen" coding rule).
