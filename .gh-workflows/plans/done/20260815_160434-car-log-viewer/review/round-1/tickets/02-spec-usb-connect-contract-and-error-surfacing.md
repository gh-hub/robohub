# 02 — [spec] Fix USB Log connect() promise contract and surface connect failures to the operator

**What to build:** Per spec.md, the USB Log Connect/Disconnect IPC actions must follow "the same 'resolves once initiated, rejects synchronously for an invalid current state' contract already used for the existing Wi-Fi connect/disconnect actions" — meaning `connect()` should always *resolve* once initiated (only rejecting synchronously if called from an invalid current state), with actual success/failure reported asynchronously via a separate status-push channel, exactly like `CarConnection`'s Wi-Fi `state-change` push does today. Currently `UsbSerialConnection.connect()` (`app/src/usbSerialConnection.ts`) instead rejects the returned promise asynchronously on failure (no CH340 found, port open failure) because no USB-Log status-push channel exists — and the only handling of that rejection today is `console.error(...)` in `app/src/renderer.ts`'s `handleUsbLogToggleClick`, so the operator sees no visible explanation when a Connect click silently fails and the button just reverts. Fix this by adding a lightweight USB Log status-push IPC channel (mirroring the existing Wi-Fi `state-change`/status pattern — subscribe function returning an unsubscribe, wired in the main process the same way the existing status-forwarding channels are), have `UsbSerialConnection` emit connect success/failure through it instead of via promise rejection, update `connect()` to always resolve once initiated (matching the Wi-Fi contract exactly), and wire the renderer to show the failure reason to the operator (e.g. in the button's status text or an inline message near the USB Log panel) instead of only logging to the console. This also directly closes the "no operator-facing error surfacing" gap noted alongside the contract mismatch.

**Blocked by:** None — can start immediately.

The synchronous "already connecting"/"already connected" `throw` at the top is untouched.
