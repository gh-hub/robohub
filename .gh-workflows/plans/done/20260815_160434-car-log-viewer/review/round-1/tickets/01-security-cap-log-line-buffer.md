# 01 — [security] Cap LogLineBuffer's unbounded pending-byte buffer

**What to build:** `LogLineBuffer.push()` (in `app/src/logLineBuffer.ts`) currently appends every incoming chunk to an internal `pending` string with no size limit, so a peer (car firmware, a LAN attacker spoofing the car's TCP endpoint, or a malfunctioning USB-serial device) sending an endless stream of bytes with no newline can grow that buffer without bound, exhausting the Electron main process's memory and crashing/hanging the app. Add a reasonable maximum size cap on `pending` (consistent with the codebase's existing 500-line panel cap philosophy — pick a sensible byte/char threshold, e.g. large enough for any real log line but small enough to bound memory, such as a few KB to tens of KB). Once the cap is exceeded without a newline arriving, discard the buffered partial data (it can never form a complete, trustworthy line anyway) rather than growing further, and resume buffering fresh from the next chunk. This must apply to both call sites that use `LogLineBuffer` — the tcp100 socket path in `app/src/carConnection.ts` and the USB serial path in `app/src/usbSerialConnection.ts` — since both share the same underlying buffer class.

**Blocked by:** None — can start immediately.

- [x] `LogLineBuffer` enforces a maximum pending-buffer size; a stream of bytes with no newline cannot grow `pending` beyond that cap — added `MAX_PENDING_LENGTH` (16 KB, exported) and a post-split length check in `push()` in `app/src/logLineBuffer.ts`.
- [x] When the cap is exceeded, the buffered partial data is discarded (not emitted as a truncated/corrupt line) and buffering resumes cleanly from the next incoming chunk — `this.pending = ""` on cap-exceeded, no line emitted for it.
- [x] A unit test proves the cap holds (feed a chunk/sequence of chunks exceeding the cap with no newline; assert `pending`/internal state does not grow unbounded and no spurious line is emitted) — two new tests in `app/src/logLineBuffer.test.ts`: one single oversized chunk, one 20-chunk cumulative-growth case proving discards happen along the way (not just a single-shot check).
- [x] Existing `LogLineBuffer` tests (multi-line chunks, CR-stripping, partial-line-across-pushes, empty lines) still pass unchanged — all 12 pre-existing tests pass unmodified.
- [x] Full test suite (`npm test` in `app/`) and typecheck (`npm run typecheck` in `app/`) still pass — 208/208 tests pass (206 + 2 new), `tsc --noEmit` clean.
