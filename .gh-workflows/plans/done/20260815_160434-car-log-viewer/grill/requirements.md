# Requirements: car-log-viewer

## Problem
The car's firmware can emit diagnostic/log text over USB serial via `Serial.println()` and potentially over the existing Wi-Fi TCP:100 socket via the firmware's `sendToClient()` method, but the app has no way to display any of it. Separately, the existing USB "connected" status badge is broken on non-macOS platforms.

## Actors
The developer/operator using the robohub Electron app to control and debug the car.

## Done looks like
- The app window shows two new scrollable, monospace log panels, "Wi-Fi Log" and "USB Log", placed below the existing connection/movement/lights/shoot/pan controls.
- **Wi-Fi Log**: while a TCP:100 (`tcp100` protocol) session is connected (via the existing Connect button — no new button), any bytes received on that socket appear as new lines in the panel, each prefixed with an app-generated receipt timestamp (e.g. `[14:32:05.123] `). When connected via the `http80` fallback protocol, or when disconnected, no new lines appear (http80 has no persistent connection to read from — this is expected behavior, not a bug).
- **USB Log**: a new, separate "Connect"/"Disconnect" button (mirroring the existing Wi-Fi toggle button's pattern) opens the detected CH340 serial port at 115200 baud and streams incoming bytes into the panel, same timestamp-prefix formatting. Disconnecting (or app close) cleanly closes the port.
- The existing USB presence badge ("USB: Connected"/"USB: Not connected") is fixed to correctly detect the car's CH340 adapter (VID `0x1A86`, PID `0x7523`) cross-platform (Windows and macOS) via `serialport`'s `SerialPort.list()`, replacing the current macOS-only `/dev/cu.usbserial-*` directory scan that always returns `false` on Windows. This badge remains passive (never opens the port) — the new USB Log Connect button is what actually opens it.
- Each log panel has its own "Clear" button, auto-scrolls to the newest line, and is capped at 500 lines (oldest dropped once exceeded). Logs are in-memory only — no disk persistence — and are NOT cleared automatically on connect/disconnect/reconnect, only by app restart or the Clear button.
- Works on both Windows and macOS.

## Out of scope
- Any firmware/`.ino` changes. This repo does not track the car's actual flashed firmware source (`docs/examples/` is reference material only, extracted from the ACECode desktop app's install — not a maintained/buildable source tree). Making the firmware emit richer log content (e.g. wiring the user's pasted `Serial.println` heartbeat into the firmware's existing `sendToClient()` method) is the user's separate task in the ACECode Block editor, not part of this plan.
- Log persistence to disk.
- A manual/dropdown serial port picker (auto-detect by VID/PID only).
- Making the Wi-Fi log work over an `http80` session (protocol has no persistent connection; this is a firmware/protocol constraint, not something the app can work around).

## Environment notes

- `app/` is an Electron desktop app (`app/package.json`: `acebott-control-app`), single `BrowserWindow` loading `app/public/index.html`, TypeScript compiled via `tsc` (main process CommonJS via `tsconfig.build.json`, renderer ESM via `tsconfig.renderer.json`). Currently zero runtime `dependencies` in `package.json` — only `devDependencies` (`@types/node`, `electron`, `typescript`).
- `app/src/carConnection.ts`: `CarConnection` (extends `EventEmitter`) owns a `net.Socket` for the TCP:100 session (`this.socket`), holds it open for the session lifetime, currently only ever *writes* to it (`sendCommandFrame`) — never attaches a `data` listener. Emits `state-change` with `{status, protocol, message}` (`protocol` is `"tcp100" | "http80" | null`).
- `app/src/usbStatus.ts`: `isUsbSerialDevicePresent()` — the confirmed bug is `if (process.platform !== "darwin") { return false; }` at line 34, which means on Windows (this dev machine's platform) this function always returns `false` regardless of whether the car is plugged in, because it then does a macOS-only `readdirSync('/dev')` scan for names starting with `cu.usbserial-`. `startUsbStatusPolling()` polls this every 2s and pushes only on change via a callback — that polling wrapper's shape can likely be reused/adapted for `serialport`'s `SerialPort.list()`.
- `app/src/main.ts`: single `CarConnection` instance owned by the main process; wires `ipcMain.handle` for each command channel; `forwardConnectionStatus()` and `startUsbStatusPolling()` both push to the renderer via `window.webContents.send(CHANNEL, payload)`, unsubscribed on window `closed`. New IPC channels for the log panels and the new USB-connect action should follow this exact established pattern.
- `app/src/ipcChannels.ts`: plain string-constant exports shared between main/preload/tests, no Electron dependency — add new channel constants here.
- `app/src/renderer.ts`: DOM-wiring only, talks exclusively to `window.carAPI` (typed via a locally-redeclared interface matching `preload.ts`'s contextBridge surface — preload.ts is CommonJS, renderer.ts is ESM, so the shape is duplicated by hand, not imported). Existing pattern: local mirrored UI state + a `render(state)` function called on every status push. New log-panel rendering should follow this same pattern.
- `app/src/preload.ts` exposes the narrow `window.carAPI` surface via `contextBridge`; `contextIsolation: true`, `nodeIntegration: false`, default (sandboxed) preload environment — preload.ts must stay self-contained (no local imports of other `app/src/` files at runtime, per `main.ts`'s comment), so any new preload-exposed methods need to be added directly there.
- Firmware ground truth (`docs/examples/QD001-V2-firmware-source/ACB_CAR_ARM.cpp`, `docs/qd001-hardware-access/protocol-reference.md`): `Carloop()` pumps the TCP:100 client socket byte-by-byte, parsing `0xFF 0x55`-framed command bytes; `sendToClient(const char* message)` writes arbitrary text back to that same open client socket — today only called from two hardcoded strings (`"Shoulder"`, `"ElbowCmd"`) on servo-limit events, not general logging.
- Confirmed hardware identity (`docs/qd001-hardware-access/hardware-identity.md`): CH340 USB-UART adapter, Vendor ID `0x1A86`, Product ID `0x7523` (QinHeng Electronics). Device previously observed as `/dev/cu.usbserial-110` on macOS (port number drifts per cable/port — do not hardcode it).
- Baud rate: **115200**, confirmed both by the pasted sketch's `Serial.begin(115200)` and by `docs/qd001-hardware-access/connecting.md`'s explicit note that `460800` fails on this adapter/cable (`Invalid head of packet (0xFF)` error) — treat 115200 as fixed, not user-configurable.
- Prior architectural decision this plan supersedes: `.gh-workflows/plans/20260815_083408-water-gun-control/grill/ADR-002.md` established that USB handling must be informational-only — a read-only filesystem presence check, macOS-only, explicitly "no open, no interaction with the device itself (no open, no serial read/write, no vendor/product ID query)". This plan's new ADR must explicitly record that it supersedes ADR-002's non-invasive constraint, since actually opening and reading the serial port is now required functionality.
- No `.ino`/firmware source is maintained anywhere in this repo as a buildable project — `docs/examples/QD001-V2-firmware-source/` and the various tutorial `.ino` files under `docs/` are reference-only copies extracted from the ACECode desktop app's install, confirmed via `docs/examples/index.md`.
