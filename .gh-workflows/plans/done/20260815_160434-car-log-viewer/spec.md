# Spec: car-log-viewer

## Problem Statement

The operator controlling the car through this Electron app has no visibility into what the car itself is saying back. The firmware can emit diagnostic text both over the Wi-Fi TCP:100 session and over the USB serial cable, but none of it is shown anywhere in the app today — the operator would have to reach for a separate serial monitor tool to see anything. Separately, the app's existing "USB: Connected"/"Not connected" badge is simply wrong on Windows: it always reports "Not connected" regardless of whether the car is actually plugged in, because the check behind it only works on macOS.

## Solution

Add two live, scrollable log panels — "Wi-Fi Log" and "USB Log" — to the existing single app window, below the current controls. The Wi-Fi Log panel automatically shows whatever text arrives on the TCP:100 socket once the operator connects via the existing Connect button; no separate control is needed for it. The USB Log panel gets its own new Connect/Disconnect button (mirroring the existing Wi-Fi one) that auto-detects the car's CH340 serial adapter by its known Vendor/Product ID and opens it at a fixed 115200 baud to stream data in. Both panels timestamp each line as it arrives, cap themselves at 500 lines, auto-scroll, and have their own Clear button. Separately, the existing USB presence badge is fixed to correctly and passively detect the CH340 adapter on both Windows and macOS.

## User Stories

1. As an operator, I want to see incoming bytes on the TCP:100 session displayed as timestamped lines in a Wi-Fi Log panel, so that I can observe car-emitted diagnostic messages while controlling it over Wi-Fi.
2. As an operator, I want the Wi-Fi Log panel to automatically start and stop receiving lines as the existing Connect/Disconnect button connects/disconnects a tcp100 session, so that I don't need a separate control to turn Wi-Fi logging on.
3. As an operator, when connected via the http80 fallback protocol (or when disconnected), I want the Wi-Fi Log panel to simply show no new lines rather than an error, so that I understand this is an expected protocol limitation, not a bug.
4. As an operator, I want a separate "Connect"/"Disconnect" button dedicated to the USB Log panel, so that I explicitly control when the app opens the car's serial port, and don't accidentally block another tool (Arduino IDE, esptool.py) that also wants exclusive access to that port.
5. As an operator, I want the USB Log Connect button to auto-detect the car's CH340 serial port by Vendor/Product ID (0x1A86/0x7523) rather than requiring me to pick a port myself, so that I don't need to know or guess the specific device path, which drifts per cable/port anyway.
6. As an operator, I want the USB Log panel to stream bytes read from the opened serial port as timestamped lines at the car's fixed 115200 baud rate, so that I can see the same kind of diagnostic output over USB as over Wi-Fi.
7. As an operator, I want the serial port cleanly closed when I click the USB Log Disconnect button or when I close the app, so that other tools can use the port immediately afterward, with no lingering lock.
8. As an operator on Windows, I want the "USB: Connected"/"Not connected" badge to correctly reflect whether the car's CH340 adapter is actually plugged in, so that the badge is finally useful on my platform (today it always reports "Not connected").
9. As an operator on macOS, I want the fixed badge to keep working exactly as well as it does today, so that fixing Windows doesn't regress the platform that already worked.
10. As an operator, I want the USB badge to remain a purely passive, read-only check that never opens the port on its own, so that the badge never contends with the USB Log Connect button (or any other tool) for exclusive access to the serial port.
11. As an operator, I want each log panel to have its own Clear button, so that I can wipe just one panel's history independently of the other, without restarting the app.
12. As an operator, I want each log panel to auto-scroll to the newest line as data arrives, so that I don't have to manually scroll to see the latest output while it's actively streaming.
13. As an operator, I want each log panel capped at 500 lines with the oldest dropped first, so that a long debugging session doesn't grow the app's memory usage without bound.
14. As an operator, I want log content to survive a disconnect/reconnect (on either panel) rather than being cleared automatically, so that I can review earlier output even after a connection drop — only an explicit Clear click or an app restart should lose it.
15. As an operator, I want both log panels visible in the same app window as the existing connection/movement/lights/shoot/pan controls, so that I can watch logs while operating the car without switching windows.
16. As an operator, I want each received log line prefixed with the app's own receipt timestamp (e.g. `[14:32:05.123]`), so that I have a rough sense of timing even though the firmware itself doesn't attach timestamps to what it sends.

## Implementation Decisions

- The module that owns the TCP:100 session gains a way to emit received socket bytes as discrete, timestamped lines, reusing the exact emitter pattern it already uses for connection-state changes — a new, additive event alongside the existing one, with no change to the existing connect/disconnect state machine. This is scoped strictly to the tcp100 protocol: an http80 session has no persistent socket to listen on, so it never emits log lines, which is expected behavior per the requirements, not an error path to handle specially.
- Incoming socket data is an unbounded byte stream, not pre-delimited lines, so this module buffers partial data and splits on newline boundaries itself, discarding the carriage-return byte `Serial.println()`-style output adds. A partial line still sitting in the buffer when the session ends is discarded rather than flushed as a truncated line — there's no guaranteed frame boundary to trust it as complete. The buffered partial line is also capped at a maximum size (`MAX_PENDING_LENGTH`, well beyond any realistic log line); if no newline arrives before the cap is hit, the buffered data is discarded rather than kept growing. This bounds memory against a peer that never sends a newline — whether misbehaving firmware or, since the tcp100 socket is unauthenticated, a spoofed/malicious peer — which would otherwise grow the buffer without bound.
- A new module owns opening, reading from, and closing the physical USB serial port for the USB Log panel. It's structured the same way the existing TCP-session module already is: constructed with injectable dependencies so tests can substitute a fake serial implementation instead of exercising real hardware or the native `serialport` bindings, exposes connect()/disconnect()-style lifecycle methods with the same "reject synchronously if called in an invalid current state" contract already established for the Wi-Fi connection, and emits discrete received lines through the same kind of emitter pattern (reusing the same buffering/newline-splitting/timestamping logic as the Wi-Fi path rather than a second copy of it).
- A shared VID/PID auto-detect helper wraps `serialport`'s port-listing call, normalizes the vendor/product ID strings it returns (the library reports them as lowercase hex with no `0x` prefix, so both sides of the comparison against the documented `0x1A86`/`0x7523` identity need normalizing) and returns the matched port's path, or none if not found. Both the presence badge and the new USB Log connect action use this one helper, so the matching rule lives in exactly one place rather than being duplicated.
- The existing presence-badge polling module is rewritten to call this same list-based helper instead of its current macOS-only directory scan, dropping the platform check entirely — enumeration behaves identically on Windows and macOS through `serialport`, so no more platform branching is needed there. Its existing "poll on an interval, push to the renderer only on change" shape is unchanged; only the underlying presence check itself changes.
- Two new push-style IPC channels forward received log lines (one per panel) to the renderer, following the exact pattern the existing status-forwarding and USB-badge-forwarding channels already use (a subscribe function returning an unsubscribe, wired in the main process the same way). Two more new channels handle the USB Log Connect/Disconnect actions themselves, following the same "resolves once initiated, rejects synchronously for an invalid current state" contract already used for the existing Wi-Fi connect/disconnect actions.
- The preload bridge gains typed methods/subscriptions mirroring the new channels, hand-duplicated the same way its existing channel constants and typed surface already are (per the established "preload stays self-contained, no local imports" constraint) — this is more entries following the existing shape, not a change to that constraint.
- The renderer gains one small, reusable piece of log-panel logic shared by both panels (append-with-cap, render-and-auto-scroll, Clear) rather than two independent copies, since the two panels differ only in which IPC subscription feeds them and which button drives their own connect/disconnect state. This follows the codebase's existing preference for small, pure, testable helper functions feeding a thin DOM-wiring layer, the same shape the connection/light/movement/shoot/pan UI-state mappers already use.
- The USB Log Connect/Disconnect button reuses the app's existing single-button toggle pattern (one button whose label and action flip based on current state), already established for the main Wi-Fi Connect/Disconnect button, rather than introducing a new interaction shape.
- `serialport` becomes the app's first runtime dependency (previously zero existed). This also introduces a native-module rebuild step for Electron's Node ABI that must be wired into the existing build/start scripts, so the packaged native binding matches Electron's runtime rather than the system Node used to run the TypeScript compiler.
- Per ADR-001, the USB presence badge stays enumeration-only and never opens the port; only the new explicit USB Log Connect action does. This is enforced structurally by keeping the badge's polling module and the new port-opening module fully separate — they share only the VID/PID lookup helper, never a "is the port currently open" flag.

## Testing Decisions

- The byte-to-line splitting and timestamp-prefixing logic (buffering partial data, splitting on newlines, discarding CRs, formatting the receipt timestamp) is pure and I/O-free enough to unit-test directly against raw byte chunks and expected line arrays — the same bar already applied to the command-frame-building and renderer UI-state-mapping pure functions in this codebase.
- The Wi-Fi log emission path is tested at the same seam the TCP connection module's existing tests already use: a real mock TCP server on an ephemeral loopback port, writing raw bytes after the client reaches connected/tcp100, asserting the emitted log-line event(s) — real sockets over loopback, not a stubbed socket layer, matching the existing file's established approach.
- The new USB-serial-owning module is tested the way the IPC handler tests already test the TCP connection module: against a narrow injectable interface with a fake, in-memory implementation standing in for the real `serialport`-backed one, so no test ever requires real hardware, the native `serialport` binding, or an actual OS serial device. The module's lifecycle contract (open/read/close, reject-synchronously-in-wrong-state) is fully verified this way; the thin adapter that actually calls into `serialport` itself is left deliberately small and is verified by manual hardware testing instead, consistent with how this codebase already treats other thin Electron/native-API adapters.
- The VID/PID matching helper is tested directly against fabricated port-list arrays (varying hex case, with and without a `0x` prefix, matching and non-matching vendor/product ID pairs) — a pure function, the same bar as the existing presence-check tests, which already inject a fake listing rather than touching a real filesystem or device.
- The rewritten presence-badge check keeps the existing "inject the underlying check function" seam its polling wrapper already provides — the check itself becomes list-based, tested by injecting a fake list-like function instead of a fake directory, while the polling/push-on-change tests around it are unaffected since that shape doesn't change. The old platform-branching tests are removed since that branch no longer exists.
- The new IPC handler additions (connect/disconnect/log-forwarding channels) are tested the same way the existing IPC handler tests already work: against a fake connection-like object, asserting the right underlying method is called and the right rejection happens in the wrong state — no real Electron `ipcMain`/`ipcRenderer` involved.
- The renderer's new log-panel append/cap/clear logic is extracted as a pure function and tested the same way the existing renderer UI-state mappers are: input in, expected resulting array out, no DOM and no browser-emulation layer. The thin DOM-wiring that calls into it is left to manual testing, matching how the rest of the renderer already splits pure logic from DOM wiring.
- End-to-end behavior against real CH340 hardware on both Windows and macOS, and a real car's firmware pushing data on the TCP:100 socket, is out of reach for the automated suite and is called out as manual verification, mirroring this codebase's existing precedent for hardware-dependent acceptance criteria (e.g. servo-direction verification).

## Out of Scope

- Any firmware/`.ino` changes, including wiring a `Serial.println` heartbeat into `sendToClient()` — that remains the user's separate task in the ACECode Block editor.
- Log persistence to disk; both panels are in-memory only.
- A manual/dropdown serial port picker — auto-detection by VID/PID is the only mechanism.
- Making the Wi-Fi log work over an http80 session — that protocol has no persistent connection to read from.
- A user-configurable baud rate — 115200 is fixed.
- Any new top-level window — both log panels live in the existing single app window.
- Auto-clearing either log panel on connect, disconnect, or reconnect.

## Further Notes

- The exact wire format of whatever the firmware eventually sends (over `sendToClient()` or over `Serial`) is unconfirmed beyond the two hardcoded strings already in the firmware today — line-splitting on newlines is the standard assumption for `Serial.println()`/typical `sendToClient()` usage, but the firmware doesn't yet emit any richer log content to verify against (wiring that up is explicitly out of scope for this plan).
- `serialport`'s native-module rebuild step for Electron (e.g. `electron-rebuild`/`@electron/rebuild`) is a new addition to this project's build tooling; the exact command/config hasn't been prototyped yet and needs to be nailed down during implementation rather than assumed correct from prose alone.
- No CH340 test hardware is available in the environment these tickets will be implemented in — USB Log streaming and the fixed presence badge both need manual verification against the real car before this plan is considered fully done, matching this codebase's existing pattern of flagging unverified hardware assumptions.
- Cross-platform `serialport` behavior (Windows COM ports vs. macOS `/dev/cu.*` paths) is assumed to be handled transparently by the library's own list/open implementation; if Windows-specific quirks (driver requirements, naming) surface during implementation, that's a risk to handle then, not something this spec resolves in advance.
- An operator could see USB Log and Wi-Fi Log content spanning multiple disconnect/reconnect cycles interleaved in each panel's history, since neither panel auto-clears. The requirements explicitly accept this ("NOT cleared automatically") as a deliberate tradeoff, not a bug — noted here so it isn't mistaken for one later.
- A narrow race exists where the app quits while a USB Log connect attempt is still in the `"connecting"` state — after the underlying `SerialPort` has been opened at the OS level but before its `"open"` event fires and `UsbSerialConnection` assigns `this.port`. In that window, `before-quit`'s cleanup (which only acts when status is `"connected"`) has no in-app reference to close explicitly. This is accepted as a known, low-risk limitation rather than fixed: process termination itself releases the OS-level serial handle, so the port is not actually left locked for other tools once the app process has exited — the gap only affects the brief interval until then, not story 7's "no lingering lock" outcome after quit. Adding extra in-flight-port tracking solely to close this narrow window was judged not worth the complexity.
