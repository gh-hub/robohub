## Draft ticket breakdown

No prefactor tickets identified — the existing frame-builder/connection/IPC-handler/UI-state-mapper seams already directly support two more device commands and one more independent push channel with pure addition, no restructuring needed. All three tickets below are vertical slices, each independently demoable, and are not blocked by each other (each touches a disjoint device code / concern; shared files like `commandFrame.ts`, `ipcChannels.ts`, `renderer.ts`, `public/index.html` are touched additively by each with no conflicting edits). Suggested implement order below is by increasing interaction complexity, not a hard dependency.

1. **Ticket: Shoot control end-to-end**
   - Blocked by: none
   - Delivers: `DEVICE_SHOOT` constant in `commandFrame.ts`; `CarConnection.shoot()` (byte-exact mock-TCP-server test + reject-when-not-connected+tcp100 tests); `car:shoot` IPC channel + handler (`FakeCarConnection`-backed test); preload exposure; a Shoot button in the UI wired to a click handler with a toggleable cooldown control, gated by the existing `connected && tcp100` rule via a new `mapShootControlUiState` pure function (unit tested across the full connection-state matrix). Demoable end-to-end: click Shoot in the running app fires one pulse on the real car; toggling cooldown on/off is manually verified.

2. **Ticket: Aim control end-to-end**
   - Blocked by: none
   - Delivers: `DEVICE_SERVO` constant in `commandFrame.ts`; `CarConnection.setAimAngle(angle)` (byte-exact mock-TCP-server tests across representative angles + reject-when-not-connected+tcp100 tests); `car:set-aim-angle` IPC channel + handler with 1-180 range validation at the trust boundary (`FakeCarConnection`-backed tests including the validation boundary, mirroring the existing movement-direction allowlist tests); preload exposure; Up/Down buttons + Fast/Slow speed dropdown in the UI wired to press-and-hold event handlers (pointerdown/up/leave/cancel + window-blur safety net, mirroring the movement D-pad's wiring) driving a throttled fixed-cadence repeat; a renderer-tracked `aimAngle` state variable (default 90, clamped 1-180, reset on connect/disconnect/error per the existing `lightsOn` reset-point precedent); a new `mapAimControlUiState` pure function covering connection-state gating plus both angle-bound edge cases (unit tested). Demoable end-to-end: holding Up/Down in the running app walks the real servo; direction sign is verified live and flipped if backwards (per ADR-001's flagged open question); bound-disabling at 1 and 180 is manually verified.

3. **Ticket: USB status badge end-to-end**
   - Blocked by: none
   - Delivers: a main-process polling subsystem that checks for `/dev/cu.usbserial-*` device nodes every 2 seconds (read-only, macOS-only) and only pushes on change; a `car:usb-status` push IPC channel, with the forwarding/subscription plumbing unit tested the same way `forwardConnectionStatus` already is (fake/stub in place of the real filesystem check); preload exposure of a `onUsbStatus`-style subscription; a small badge UI element next to the existing Wi-Fi status text, updated reactively by a renderer listener with no local polling or state of its own. Demoable end-to-end: plugging/unplugging a USB-serial cable in the running app updates the badge within ~2 seconds; confirmed to have zero effect on the Wi-Fi Connect/Disconnect button or any car command.
