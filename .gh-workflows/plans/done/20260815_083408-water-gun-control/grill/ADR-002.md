# ADR-002: USB Connection Status Is Informational Only, Not a Control Channel

## Status
Accepted

## Context

During the grill interview, the user asked whether a USB-serial connection could be used as an alternative command channel, replacing or disabling the existing Wi-Fi "Connect" button to send car commands over USB instead of Wi-Fi TCP:100. This question led to a critical discovery through static firmware analysis: **the USB-serial channel (Serial/UART) in the firmware is used for debug output only and contains no code path that parses binary command frames**.

The ACEBOTT QD001 firmware is structured with:
1. A `WiFiServer server(100)` on port 100 that receives and parses binary command frames (0xFF 0x55 …) via TCP/IP.
2. A `Serial` object (USB-serial connection on macOS/Linux, or UART on physical boards) that is used exclusively for `Serial.print()` debug output.

There is no overlap, no command parsing off Serial, and no way for the firmware to execute car commands via a USB connection with the current codebase. Confirming this required reading the complete firmware source (both `acebott-esp32-car-shoot-005.ino` and the base QD001 reference code) and verifying that the only reads from Serial are in the form of `Serial.available()` polling for debug REPL input, not for command-frame parsing.

### Why USB connection appeared viable initially

The physical car hardware has a USB-serial port. The ACEBOTT documentation mentions "USB connection" as a way to connect to the car. This created a reasonable initial assumption that if Wi-Fi can send commands, USB might too. However, the assumption was based on documentation-level descriptions, not firmware-source analysis. The reality is that the USB connection is for:
- Flashing/reprogramming the firmware (ESPtool.py, Arduino IDE)
- Reading debug Serial.print() output
- Never: parsing and executing car commands

### Current app's USB handling

The app currently has no USB-specific code. There is an existing `docs/qd001-hardware-access/index.md` file documenting the device-node detection method (`/dev/cu.usbserial-*` on macOS), but this is used only as a reference for developers, not integrated into the app's control flow.

### Decision: Informational badge, not a control channel

Given the firmware's USB-parse limitation, the original request ("USB connection replaces Wi-Fi button") is **technically infeasible without new firmware work**. However, the user expressed genuine interest in knowing when the car is physically plugged in via USB, even if no commands can be sent over USB. This led to the compromise: add a small, purely informational status badge that displays USB-connected / disconnected status, independent of and without affecting the Wi-Fi control system.

## Decision

Add a non-functional, read-only USB connection status badge to the UI, implemented as a simple, low-overhead polling mechanism in the Electron main process:

### 1. Detection mechanism

- **Polling target**: The Electron main process periodically (every 2 seconds) checks for the presence of device nodes matching the pattern `/dev/cu.usbserial-*` using a read-only filesystem operation (glob, ls, or fs.statSync on `/dev/cu.*`).
- **Platform scope**: macOS only (consistent with existing project tooling; Windows/Linux can be added later if needed, but are out of scope for this plan).
- **Non-invasive**: The check does NOT open or interact with the device node itself. It does NOT run `esptool.py`, does NOT attempt to open a serial port, does NOT send any data to the device, does NOT call `lsusb` or vendor/product ID queries. It is a pure filesystem metadata check.
- **Push via IPC**: The main process publishes USB status updates via a new IPC push channel `car:usb-status` (main→renderer), mirroring the existing `car:status` push pattern already used for Wi-Fi connection state updates. The payload is a small object or boolean indicating connected/disconnected.
- **Cadence**: Status updates are pushed to the renderer whenever the detection poll detects a change (transition from no device to device present, or vice versa). Continuous polling every 2 seconds is cheap enough (filesystem glob on a small directory) not to require UI throttling.

### 2. Renderer-side display

- Add a small status badge text element (e.g., "USB: Connected" / "USB: Not connected") displayed next to the existing Wi-Fi connection status indicator. This is purely cosmetic and does not gate or enable any functionality.
- The badge updates reactively when `car:usb-status` push events arrive from the main process.

### 3. Interaction model: Display-only, no control

- The USB badge does NOT disable, replace, or interact with the existing Wi-Fi "Connect"/"Disconnect" button in any way. Wi-Fi remains the sole command channel.
- No car commands (shoot, aim, lights, movement, or any other) can be sent over USB. Attempting to do so would fail; it is not supported by the firmware.
- The badge is informational: "the car is plugged in via USB right now" (true/false). That is its only purpose.
- Users who want to control the car must still use Wi-Fi, regardless of USB connection status.

### 4. Known limitation, accepted: False positives

- The detection mechanism only checks for the `/dev/cu.usbserial-*` device-node naming pattern. It does NOT verify the device's USB vendor/product ID against the car's known values.
- If any other unrelated USB-serial device (e.g., an Arduino, a prolific USB-serial adapter, a different robot) happens to be plugged in, the badge will show "USB: Connected" even though the car is not plugged in.
- This false-positive risk is **accepted** because:
  - The badge has no functional impact (does not gate or enable any control).
  - The risk is cosmetic (a false status indicator), not a safety or correctness issue.
  - Adding vendor/product ID filtering would require additional device metadata queries (`lsusb`, system calls, or attempting to open the device to read its descriptor), which violates the "read-only, non-invasive" design principle.
  - Users can disambiguate if needed by unplugging all USB devices and re-plugging the car specifically.

## Rationale

- **Why informational, not a control channel**: The firmware has no serial-command-parsing code path (verified by source analysis). Adding USB-based commands would require new firmware development, which is out of scope. An informational badge fulfills the user's stated need to know about USB connection status without promising capabilities the firmware cannot deliver.

- **Why a polling badge, not a deeper integration**: Unlike Wi-Fi connection (which the app actively initiates and manages), USB connection is passive — the user physically plugs/unplugs the device. A simple polling mechanism (every 2 seconds, cheap filesystem check) is appropriate for detecting these rare user-initiated events. It requires no active device interaction, no blocking operations, and no driver integration.

- **Why `/dev/cu.usbserial-*` pattern and macOS-only**: This is the standard macOS device-node pattern for USB-serial adapters (consistent with existing documentation in `docs/qd001-hardware-access/index.md`). Platform-specific code is acceptable for hardware integration tasks. Windows/Linux patterns can be added in a future plan if needed.

- **Why 2-second polling interval**: USB plug/unplug events are rare and user-initiated (not time-critical). A 2-second interval is a good balance between responsiveness (user sees the badge update within 2 seconds of plugging in) and efficiency (negligible CPU cost for a filesystem glob operation). More frequent polling provides no benefit.

- **Why accepting false positives**: Attempting to eliminate false positives would require intrusive operations (opening device nodes, querying descriptors, calling vendor-specific tools) that violate the "read-only, non-invasive" design principle established in the project's hardware-interaction guidelines. Since the badge has no functional impact, false positives are a cosmetic inconvenience, not a correctness issue. The simpler design is worth the tradeoff.

## Consequences

- The app now displays USB-connected / disconnected status as a non-functional badge, giving users passive awareness of whether the car is physically plugged in via USB.
- A new IPC push channel `car:usb-status` is added to the app's architecture, following the pattern of `car:status`.
- The Electron main process adds a 2-second polling timer that checks `/dev/cu.usbserial-*` device nodes at startup and whenever the poll runs. This is a negligible performance cost.
- The renderer adds a small UI element and a listener for the `car:usb-status` event. The element updates whenever USB status changes.
- **Known risk**: The badge may show false positives if other USB-serial devices are present. Users should not rely on it as a definitive indicator of car connection; it is informational only.
- **Not tested for other USB-serial patterns**: Windows (`COM*` ports) and Linux (`/dev/ttyUSB*` ports) have different naming patterns. Adding support for these platforms is out of scope for this plan but can be added in future work if needed (each platform gets its own detection logic).
- **No firmware changes required**: This entire feature is app-side only and does not depend on or interact with any firmware modifications. USB remains a debug-output-only channel in the firmware.
