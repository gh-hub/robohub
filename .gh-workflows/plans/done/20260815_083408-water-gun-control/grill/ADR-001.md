# ADR-001: QD005 Servo/Shoot Command Protocol and Press-and-Hold Aim Model

## Status
Accepted

## Context

The ACEBOTT QD005 water gun attachment adds two new command capabilities to the QD001 car. The binary command-frame protocol (0xFF 0x55 <length=0x0A> <10-byte payload>, established in previous plans and documented in those plans' ADRs) is being extended to support these two new devices via device codes reverse-engineered from the ACEBOTT firmware source.

Unlike the lights (device 0x05, simple on/off) and movement (device 0x0C, directional stop/go) commands already implemented and confirmed working on real hardware, the QD005 commands (device 0x02 for servo, device 0x08 for shoot) have never been live-tested on this physical unit before. This ADR documents the protocol facts discovered through static firmware analysis and the interaction model chosen to safely and responsively drive this previously-unverified hardware.

### QD005 protocol reverse-engineered from firmware source

The device codes and command handling were reverse-engineered from two byte-identical firmware implementations:

1. **QD005 source**: `docs/ACEBOTT QD005 Shooting Car V1 Tutorial V2.9/Arduino(Experienced Learner)/ACEBOTT QD005 ESP32 Shooting Car A/2.Program file/acebott-esp32-car-shoot-005/acebott-esp32-car-shoot-005.ino`
2. **QD001 base source**: `docs/ACEBOTT QD001 - smart car - base/Arduino(Experienced Learner)/5.Program file/7_4APP_control_car/7_4APP_control_car.ino`

Both define byte-identical `runModule(int device)` handling for the two new device codes below. The command-handling code is shared ACEBOTT template firmware baked into the entire product family, not specific to a single kit variant. Cross-reference verification: The unique strings `"Firmware Version is 0.12.21"` and `"Camera Ready! Use 'http://"` appear in both the actual firmware dump at `tools/qd001-probe/dumps/app0_strings.txt` and in the `acebott-esp32-car-shoot-005.ino` source, confirming that the currently-flashed firmware on the physical car is the QD005-compatible version and already contains the device 0x02 and 0x08 command handlers.

### Protocol facts: Servo (device 0x02)

- **Device code**: `0x02` (aim servo)
- **GPIO**: 26 (`TURN_SERVO_PIN`)
- **Value semantics**: The command-frame's single value byte (payload[9]) is interpreted as an **absolute angle 1–180 degrees** (inclusive, the firmware's supported range).
- **Firmware handling**: The firmware's `Servo_Move(val)` function maps this angle to a PWM value via `map(angles, 1, 180, 130, 70)` (angle 1 → PWM 130, angle 180 → PWM 70), then smoothly interpolates the servo from its current position to the target PWM value over approximately 15–20 steps with 20ms delays between steps, totaling ~300–400ms per command. **This entire interpolation blocks the firmware's TCP receive loop** — the firmware cannot accept a new command frame while a previous angle-move is still interpolating.
- **Boot default**: The firmware's `setup()` initializes the servo to angle 90 at boot time (`turnServo.write(angle)` where `angle = 90`).

### Protocol facts: Shoot (device 0x08)

- **Device code**: `0x08` (blaster trigger)
- **GPIO**: 32 (`Shoot_PIN`)
- **Value semantics**: The command-frame's value byte is **completely ignored** by the firmware. Any frame with `action=CMD_RUN, device=0x08` triggers a shot regardless of value.
- **Firmware handling**: The firmware's handler is `digitalWrite(Shoot_PIN, HIGH); delay(200); digitalWrite(Shoot_PIN, LOW);` — a fixed 200ms pulse that triggers the blaster mechanism. This pulse **also blocks the firmware's TCP receive loop** for the duration of the 200ms pulse.
- **No stop semantics**: Unlike movement commands which require explicit Stop (value 0x00) to halt the motors, the shoot command is self-contained. The 200ms pulse is managed entirely by the firmware; there is no separate "stop shooting" command. One frame triggers exactly one 200ms pulse.

### Protocol limitation: One-directional, fire-and-forget

The binary command protocol (lights, movement, and now shoot/aim) is **one-directional** — it has no state-readback channel. The renderer sends commands to the main process, which sends frames to the car, but there is no way to query the servo's current angle or any other car state from the protocol itself. This is an established architectural limitation inherited from all prior command implementations.

### Critical interaction design fact: Firmware blocking

Both device 0x02 (servo) and device 0x08 (shoot) block the firmware's TCP receive loop while executing. Device 0x02 blocks for ~300–400ms per command, device 0x08 for 200ms per command. If the app sends rapid-fire commands faster than the firmware can process them (i.e., multiple commands within the interpolation/pulse window), the frames will back up in the TCP buffer, causing visible lag or stuttering in the motion response. This is a fundamental constraint of the hardware and drove the design decision for the aim interaction model (press-and-hold with throttled repeat, not rapid clicks).

## Decision

Implement QD005 servo and shoot commands using two new device codes in the existing binary command-frame format, with a press-and-hold aim interaction model and a single-click shoot interaction model:

### 1. Protocol: Device codes and constants

- Add to `app/src/commandFrame.ts`:
  - `DEVICE_SERVO = 0x02` (aim servo)
  - `DEVICE_SHOOT = 0x08` (shoot blaster)
  - Value constant for shoot (since value is ignored by firmware, use `0x00` by convention)
  - Both use the existing `action = CMD_RUN (0x01)` already defined and used by lights and movement

### 2. IPC channels and handlers

- New IPC channels in `app/src/ipcChannels.ts`:
  - `car:set-aim-angle` (main->renderer push and renderer->main invoke) carrying an absolute angle number (1–180)
  - `car:shoot` (renderer->main invoke) with no arguments
- New handlers in `app/src/carIpcHandlers.ts`:
  - `handleSetAimAngle(angle: number)` — validates angle is 1–180, sends device 0x02 command
  - `handleShoot()` — sends device 0x08 command with value 0x00
- New methods in `app/src/carConnection.ts`:
  - `setAimAngle(angle: number)` — constructs and sends device 0x02 frame
  - `shoot()` — constructs and sends device 0x08 frame

### 3. App-tracked state (no protocol readback exists)

- Add a renderer-side `aimAngle` state variable, initialized to 90 (firmware's boot default).
- Reset `aimAngle` to 90 on every fresh connect, disconnect, or error status change — the same reset points used for the existing `lightsOn` app-tracked boolean. Do NOT reset during the `"connecting"` transient state.
- This mirrors the established precedent for app-tracked state that cannot be queried from the car (no protocol readback channel exists).

### 4. Aim interaction model: Press-and-hold with throttled repeat

- **Buttons**: Add Up and Down buttons next to a speed dropdown selector.
- **Speed dropdown**: Two fixed options, "Fast" and "Slow", with "Fast" as default. "Fast" = 10° per step, "Slow" = 5° per step. The currently-selected speed determines the step size for held button repeats.
- **Cadence**: While a button is held, repeat the increment/decrement at a fixed 400ms interval. The 400ms interval matches the firmware's own blocking interpolation time (~300–400ms), ensuring only one angle command is ever in flight and preventing TCP buffer backlog.
- **Bounds**: App-tracked angle is clamped to 1–180 (firmware's supported range). Up button is disabled when angle ≥ 180; Down button is disabled when angle ≤ 1.
- **Direction sign (unverified)**: As a starting assumption, Up increases angle and Down decreases angle. This is explicitly unverified against the physical hardware — the firmware's internal PWM mapping inverts the relationship, and which physical direction (barrel tilting up vs down) that produces on the real QD005 mount is unknown until tested live. If the live hardware test shows this is backwards, it is a one-line sign flip in the increment logic, not a redesign. This must be verified during the implement phase.

### 5. Shoot interaction model: Single-click with toggleable cooldown

- **Button**: A single "Shoot" button, distinct from Aim.
- **Click behavior**: One click sends exactly one device 0x08 command frame, triggering one 200ms pulse.
- **Cooldown toggle**: Add a separate toggle control (on/off) that gates whether the Shoot button disables itself after each click. When on (default), the button disables for ~300ms (200ms firmware pulse + 100ms margin) before re-enabling, preventing button-mash rapid-fire behavior. When off, the button re-enables immediately and can be clicked repeatedly with no artificial delay. The cooldown is a user-selectable toggle, not a fixed always-on behavior.

### 6. Gating and enablement

- Both Aim and Shoot controls are enabled only when `connection.status === "connected" && connection.protocol === "tcp100"`.
- This directly reuses the existing gating rule from `mapLightControlUiState` / `mapMovementControlUiState` in `app/src/connectionUiState.ts`.
- All three control groups (Lights, Movement, Aim, Shoot) are disabled in every other state: disconnected, connecting, error, or connected over http80 fallback.

## Rationale

- **Why this protocol**: The device codes 0x02 and 0x08 are reverse-engineered from the ACEBOTT firmware source code itself, which is authoritative. Using the same frame shape as lights and movement (action/device/value split) keeps the command architecture unified and leverages the existing `buildCommandFrame()` pure function. The currently-flashed firmware already contains these handlers (confirmed via string cross-reference), so no hardware reflash is needed.

- **Why press-and-hold with 400ms throttle for aim**: The firmware blocks the TCP loop for ~300–400ms per servo command. If the app sends commands faster than this, frames queue up, causing visible lag. The 400ms repeat interval ensures only one command is ever in flight, avoiding backlog. Press-and-hold gives users real-time visual feedback (holding = moving, releasing = stopping) and matches the interaction feel of the existing movement D-pad. A simpler click-to-step model was rejected because it lacks this real-time feedback and would feel less responsive in comparison to movement.

- **Why user-selectable step size (Fast/Slow)**: The user wanted runtime flexibility to experiment with different aim speeds rather than a single fixed step size. The dropdown implements this without complicating the interaction — it's a one-time choice per session, not a per-click decision.

- **Why 1–180 bounds clamping**: The firmware's `map(angles, 1, 180, 130, 70)` will extrapolate PWM values outside the safe 70–130 range if given angles outside 1–180, risking servo over-drive or damage. Clamping app-side prevents this and ensures the servo is always driven within safe parameters. Disabling buttons at bounds matches the established disabled-button UX convention used elsewhere (e.g., movement/lights gated by connection state).

- **Why single-click shoot, not press-and-hold**: The firmware's shoot handler is fire-and-forget — a fixed 200ms pulse triggered once per command. There is no variable-duration or press-to-stop semantics. Holding a button longer does not extend the pulse, so press-and-hold has no meaningful effect. A single-click model is the only one that matches the actual firmware behavior.

- **Why toggleable cooldown, not fixed**: The user wanted the ability to experiment with rapid-fire clicking when desired, while defaulting to the safer button-mash-prevention behavior. Making it a toggle honors both use cases.

- **Why app-tracked angle with no readback**: The protocol has no state-query channel. The app must track the current angle locally and reset it on connect/disconnect/error to avoid carrying stale assumptions across reconnects. This mirrors the precedent set by the `lightsOn` boolean, which is also app-tracked with no hardware readback.

- **Why unverified direction sign, deferred to hardware test**: The firmware's internal PWM mapping (angle 1 → PWM 130, angle 180 → PWM 70) inverts the relationship between angle values and PWM direction. Which physical direction the servo horn moves for a given PWM value depends entirely on how the horn is physically mounted on this specific QD005 unit. There is no way to determine this from static source analysis alone. This must be verified during implementation by observing the real hardware. If backwards, it's a trivial fix (one-line sign flip), not a design issue.

- **Why live hardware verification is required**: Unlike lights (simple on/off, easy to infer from names) and movement (tested and confirmed working in the prior plan), servo and shoot commands have never been live-tested on this car before. The firmware source analysis is thorough but not a substitute for real hardware testing. The interaction model (press-and-hold with throttle, direction signs) and all cooldown logic must be manually verified working against the real car before this can be considered complete.

## Consequences

- The app can now control the QD005 shoot trigger (single-click, optional cooldown) and aim servo (press-and-hold, user-selectable 5–10° steps at 400ms cadence, clamped to 1–180°).
- Two new command devices (0x02, 0x08) are added to the existing binary frame protocol. The frame format itself (0xFF 0x55 <length> <payload>) remains unchanged, leveraging existing frame builders.
- Two new IPC channels are added (`car:set-aim-angle`, `car:shoot`), following the established naming and parameterization pattern of `car:set-lights` and `car:set-movement`.
- Two new protocol handler functions and two new `CarConnection` methods are added, following the established testing pattern: pure functions (frame builders, UI-state mappers) are unit tested; IPC handlers are tested via `FakeCarConnection`.
- Renderer-side press-and-hold logic (timers, throttle, active-direction tracking for aim) and cooldown toggle wiring are new DOM-level code not present in prior plans. This logic is **manually verified against real hardware**, not unit tested, per the established convention set by the movement plan's ADR-001.
- The app now depends on accurate live-hardware verification of aim direction signs and the interaction responsiveness of both shoot and aim commands. Manual testing during the implement phase is not optional — it is a critical gate for completion, since this is the first time these devices are being live-tested on this hardware.
- **Not yet live-tested**: This entire ADR describes protocol and interaction behavior that has never been verified against the real physical car. Testing must happen during implementation and must succeed before this plan can be marked done. This is a fundamental difference from the lights and movement plans, which document already-confirmed-working features.
