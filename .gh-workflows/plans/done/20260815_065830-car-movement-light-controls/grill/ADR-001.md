# ADR-001: Movement Command Protocol and Press-and-Hold Safety Model

## Status
Accepted

## Context

The ACEBOTT QD001 smart car firmware supports direct motor control via binary command frames sent over TCP port 100. The base frame format (0xFF 0x55 <length> <10-byte payload>, with action at payload[6], device at payload[7], and value at payload[9]) was established in the previous plan ("car-lights-control") and is documented in that plan's ADR-001 at `.gh-workflows/plans/done/20260814_195843-car-lights-control/grill/ADR-001.md`. This ADR builds on top of that base format.

The previous plan established lights (LED, device 0x05, value 0/1) over this frame format. This plan extends the same frame format to movement (motor, device 0x0C, value byte per direction), and establishes the press-and-hold interaction model that is necessary due to a critical firmware safety fact: the firmware has no automatic stop-on-timeout for direct CMD_RUN commands.

### Movement protocol reverse-engineered from firmware

The device code and value table for movement were reverse-engineered from the ACEBOTT QD001 reference firmware's `runModule()` function:

- **Arduino source**: `docs/ACEBOTT QD001 - smart car - base/Arduino(Experienced Learner)/5.Program file/7_4APP_control_car/7_4APP_control_car.ino`
- **Python source**: `docs/ACEBOTT QD001 - smart car - base/Python/5.Python Program/7.4APPControlCar.py`

The implementations are byte-identical, giving high confidence in the protocol. The motor control section uses:
- `action = 0x01` (CMD_RUN, same as LED commands)
- `device = 0x0C` (motor/movement)
- `value` byte per direction:
  - 0x00: Stop
  - 0x01: Forward
  - 0x02: Backward
  - 0x03: Move_Left (arc turn)
  - 0x04: Move_Right (arc turn)
  - 0x09: Contrarotate (pivot turn, counter-clockwise, called "Rotate Left")
  - 0x0A: Clockwise (pivot turn, clockwise, called "Rotate Right")

(The firmware also defines diagonals at 0x05-0x08, which are intentionally out of scope for this plan.)

### Critical safety fact: No watchdog for CMD_RUN

The firmware has **no automatic stop-on-timeout for direct CMD_RUN movement commands**. Unlike some RC protocols with watchdog timers, once a direction value is sent via CMD_RUN, the motors keep running at that direction indefinitely — **the only way to stop them is an explicit Stop (value 0x00) command frame**.

The firmware does have a 3-second `lastDataTimes` timeout, but it **only applies to auto-drive modes** (line-follow, obstacle-avoidance, when `st = true`), not to direct CMD_RUN commands. This is a critical safety fact that drove the interaction-model design.

## Decision

Implement movement control as a press-and-hold interaction that sends explicit Stop commands on multiple safety-trigger events:

1. **Protocol**: Use the existing binary command-frame format with `action = CMD_RUN (0x01)`, `device = 0x0C`, and direction-specific value bytes as documented above. No changes to the frame format itself (see base ADR-001 for that format).

2. **Interaction model**: 
   - `pointerdown` on a direction button sends that direction's command frame immediately.
   - `pointerup` sends Stop (value 0x00).
   - `pointerleave` or `pointercancel` (pointer left bounds while still held) sends Stop.
   - `window.blur` (window lost focus, e.g., alt-tab) sends Stop.
   - Connection drop (status left `connected`+`tcp100`) sends Stop if still possible.
   - The app tracks a single `activeDirection` state; pressing a new direction immediately overwrites and sends it (interrupt semantics, not queueing). Only the event that matches `activeDirection` can send Stop — a mismatched event is a no-op.

3. **Gating**: Movement buttons are enabled only when `status === "connected" && protocol === "tcp100"`, reusing the same gate as lights. HTTP:80 has zero command support.

## Rationale

- **Why this protocol**: It matches the firmware's actual implementation (reverse-engineered from Arduino and Python reference code, byte-identical in both). Using the same frame shape as lights (action/device/value split) keeps the command architecture consistent and leverages the existing `buildCommandFrame` pure function.

- **Why press-and-hold with explicit Stops**: The lack of a watchdog is a safety-critical fact. A simple click handler or mouseup-only stop leaves the motors running if the pointer leaves the button, the window loses focus, or the connection drops. Sending Stop on all these events ensures the motors cannot be left running uncontrollably. The press-and-hold model also gives users real-time feedback (holding = moving, releasing = stopping) that matches their mental model of car control.

- **Why interrupt semantics with active-direction matching**: If a user presses Forward then Left without releasing Forward, they expect the car to immediately turn left. If they then release Forward (still holding Left), the old Forward release should NOT send Stop. The single `activeDirection` slot and matching rule enforce this: only an event that corresponds to the currently-tracked direction can send Stop. This makes the interrupt-press behavior intuitive and safe.

- **Why gating identical to lights**: Movement commands only work over TCP:100. Disabling buttons when disconnected, connecting, in error state, or over HTTP:80 prevents user confusion and rejected commands.

## Consequences

- The app can now drive the car in six directions (Forward, Backward, Left, Right, Rotate Left, Rotate Right) with press-and-hold control and explicit motor stops.
- The press-and-hold model requires renderer event wiring (pointerdown, pointerup, pointerleave, pointercancel, blur) and active-direction state tracking in the renderer. This is new DOM-level logic not present in the lights plan.
- Motor safety is contingent on the renderer correctly sending Stop on all required events. The manual verification step during implementation (testing interrupt semantics and all stop-trigger paths against real hardware) is critical and should not be skipped.
- The value table (0x00-0x04, 0x09-0x0A) is implemented as named constants in `commandFrame.ts`, e.g., `MOVE_STOP = 0x00`, `MOVE_FORWARD = 0x01`, etc., or an equivalent enum/object — whichever fits the file's existing style.
- The IPC channel `car:set-movement` carries a direction string (`"forward"`, `"backward"`, `"left"`, `"right"`, `"rotate-left"`, `"rotate-right"`, `"stop"`) and is mapped to numeric values inside `CarConnection.setMovement()` or a mapping function.
- Both pure functions (frame builder, UI-state mapper) and `CarConnection.setMovement()` are covered by unit tests. IPC handlers are tested via `FakeCarConnection`. DOM wiring (event handlers, active-direction state) is manually verified against hardware, per established convention.
