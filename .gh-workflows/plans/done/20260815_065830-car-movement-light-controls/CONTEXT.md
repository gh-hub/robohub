# Context: car-movement-light-controls

## What we're building
Consolidate the two mirrored "Left Light"/"Right Light" buttons into one "Lights" button, and add press-and-hold movement controls (Forward, Backward, Left, Right, Rotate Left, Rotate Right) to the ACEBOTT control app, sent over the existing TCP:100 command-frame protocol.

## Key decisions
- Lights: UI-only simplification, one button instead of two — no protocol change (the wire command was always shared).
- Movement: press-and-hold interaction, with Stop sent on pointerup, pointer-leave-while-held, window blur, or disconnect — the firmware has no watchdog, so a direction command drives the motors indefinitely until an explicit Stop arrives.
- Movement protocol: device 0x0C (motor), action CMD_RUN (0x01, reused from lights), value byte per direction (Stop 0x00, Forward 0x01, Backward 0x02, Left 0x03, Right 0x04, Rotate Left 0x09, Rotate Right 0x0A) — reverse-engineered from 7_4APP_control_car.ino / 7.4APPControlCar.py.
- One parameterized IPC channel for movement (car:set-movement), same pattern as lights (car:set-lights).
- D-pad layout (Forward/Backward/Left/Right in a cross, rotate buttons below).
- New press interrupts an active direction; a release only sends Stop if it matches the currently-active direction.

## Gotchas
- Ticket 01: `mapLightControlUiState` in `connectionUiState.ts` was already a single mirrored-result function (no per-button left/right logic to begin with), so consolidating to one button was a pure DOM/HTML change with no pure-logic seam to add tests around — spec.md's Testing Decisions already anticipated this ("no new tests needed"). Stale doc comments referencing "Left Light"/"Right Light" existed in `connectionUiState.ts` and `preload.ts` (not just `renderer.ts`/`index.html`) — worth grepping for old button-name references across the whole `app/src` tree, not just the files a ticket names, when doing similar UI renames.
- `general.md`'s "verify with Playwright" UI rule was not followed for ticket 01 — Playwright isn't set up in this Electron app, and spec.md's Testing Decisions explicitly call for manual verification of DOM/pointer wiring instead, consistent with the pre-existing convention from the prior lights plan. Noted as a conflict in `PROGRESS/notes/implement-01-lights-single-button.md` rather than silently skipped; a human hardware click-through of the Lights button is still recommended before merging.
- The car firmware has NO auto-stop watchdog for direct movement commands (CMD_RUN on device 0x0C) — once a direction is sent it drives forever until Stop (value 0x00) is sent. This is why the press-and-hold interaction must cover pointerup, pointer-leave, window blur, and disconnect, not just a simple click handler.
- The frame format itself (0xFF 0x55 <len> <payload>, action at payload[6], device at payload[7], value at payload[9]) is unchanged from the existing lights implementation — see the previous plan's ADR-001 at .gh-workflows/plans/done/20260814_195843-car-lights-control/grill/ADR-001.md. This plan only adds a new device code (0x0C) and its value table; it does not change buildCommandFrame()'s shape.
- Ticket 02 is done. Protocol layer API for ticket 03 to consume directly: `app/src/commandFrame.ts` exports `DEVICE_MOTOR = 0x0c`, `type MovementDirection = "stop" | "forward" | "backward" | "left" | "right" | "rotate-left" | "rotate-right"`, and `MOVEMENT_VALUES: Record<MovementDirection, number>`. `app/src/carConnection.ts`'s `CarConnection` class exports `async setMovement(direction: MovementDirection): Promise<void>`, with the exact same gating/rejection contract as `setLedState()` (rejects synchronously when disconnected or on http80, via the shared `sendCommandFrame()` guard — no new gating logic exists to duplicate). The `MovementDirection` string literals match ADR-001's stated `car:set-movement` IPC payload strings exactly, so ticket 03's IPC handler can pass the payload straight through to `setMovement()` with no extra mapping step, as long as the renderer emits these exact literals (note the hyphenated `"rotate-left"`/`"rotate-right"`, not camelCase or underscored).
- Full details and the test coverage added for ticket 02 are in [PROGRESS/notes/implement-02-movement-protocol-layer.md](PROGRESS/notes/implement-02-movement-protocol-layer.md).
- Ticket 03 is done. `app/src/renderer.ts` (and `preload.ts`) deliberately redeclare `MovementDirection` locally rather than `import type` it from `commandFrame.ts` — `commandFrame.ts` is part of the CommonJS main-process build (tsconfig.build.json), and pulling it into renderer.ts's separate ES-module compilation unit (tsconfig.renderer.json) risks tsc emitting a clobbering ESM copy of `dist/commandFrame.js` over the CJS one main.ts/carIpcHandlers.ts need — the exact same failure mode already documented at the top of renderer.ts for `carConnection.ts`/`ConnectionState`. preload.ts, being CommonJS itself, safely imports the type directly. Keep the redeclared literal union in renderer.ts in sync by hand if `commandFrame.ts`'s `MovementDirection` ever changes.

- Both round-1 fix tickets are complete, but round-2 review caught that fix 02's `value in MOVEMENT_VALUES` check walks the prototype chain — inherited `Object.prototype` property names (`"constructor"`, `"toString"`, `"hasOwnProperty"`, `"valueOf"`, `"__proto__"`, `"isPrototypeOf"`, `"propertyIsEnumerable"`, `"toLocaleString"`) passed the allowlist check and would have resolved to a non-numeric `MOVEMENT_VALUES[value]`, silently coerced to byte 0 in the command frame — the same bug class fix 02 was meant to close, just narrower. Round-2 fix 01 closed this: `isMovementDirection()` now uses `Object.prototype.hasOwnProperty.call(MOVEMENT_VALUES, value)` instead of `in`. TDD'd with 8 new tests (one per inherited name), confirmed to fail against the old `in`-based check and pass after the one-line fix. Full suite 86/86 pass, typecheck and build both clean. Full detail: [PROGRESS/notes/implement-review-round-2-fix-01-prototype-chain-allowlist-bypass.md](PROGRESS/notes/implement-review-round-2-fix-01-prototype-chain-allowlist-bypass.md).
- **Gotcha for future allowlist checks in this codebase:** never use the `in` operator for membership checks against a plain object literal used as a lookup table — it walks the prototype chain and passes inherited `Object.prototype` names. Use `Object.prototype.hasOwnProperty.call(obj, key)`, a `Set`, or an explicit array with `.includes()` instead. This is now the second review round in this plan to catch a variant of "unvalidated/under-validated string resolves silently to byte 0 instead of being rejected" — worth a deliberate look in round-3 for any other place a similar pattern could hide.
