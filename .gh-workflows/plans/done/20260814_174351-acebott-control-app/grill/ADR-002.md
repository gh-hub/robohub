# ADR-002: Electron Main Process Owns the TCP Socket

**Status:** Accepted

## Context

The Electron app needs to maintain a TCP connection to the ACEBOTT car and manage its lifecycle (connect, disconnect, detect drops). Electron architecture separates the main process (Node.js) from the renderer process (web UI), and IPC is the standard way they communicate.

A decision was needed about where to place the TCP socket logic: in the main process or in the renderer. The renderer could theoretically use Node.js APIs directly if Node integration were enabled, but this would break Electron's security model.

## Decision

The Electron main process (Node.js) will own and manage the TCP connection using Node's built-in `net` module. The renderer process (the HTML/CSS/JavaScript UI) will interact with the connection only via:

- IPC messages (e.g., `ipcRenderer.send('connect')`, `ipcRenderer.send('disconnect')`)
- A preload script that exposes only safe, declared APIs to the renderer
- Event listeners on the renderer side for status updates from the main process

The renderer will never perform raw socket I/O directly, and Node integration will not be enabled in the renderer.

## Consequences

- **Security:** Maintains Electron's process-isolation sandboxing. If the renderer is compromised, it cannot directly access system resources or the socket.
- **Stability:** The main process can manage the socket lifecycle robustly without interference from renderer reloads or crashes.
- **Code clarity:** Socket logic is centralized in one place (main process) rather than split across processes, making it easier to understand and maintain.
- **IPC overhead:** All socket operations incur a small IPC round-trip cost, but this is negligible for the low-frequency operations needed (connect, disconnect, status polling).
- **Error handling:** Socket errors and disconnections are handled in the main process and communicated to the renderer via IPC, ensuring the UI always stays in sync with the actual connection state.
