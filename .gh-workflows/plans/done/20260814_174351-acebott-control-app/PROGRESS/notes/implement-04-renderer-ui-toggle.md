- **`app/src/connectionUiState.ts`** — the pure `ConnectionStatus → UI state` mapping function, `mapConnectionStatusToUiState(state: ConnectionState): ConnectionUiState`. No DOM access. Covers all 4 states via an exhaustive `switch`:
  - `disconnected` → button "Connect" (enabled), status "Disconnected", class `status-disconnected`
  - `connecting` → button "Connecting…" (disabled), status "Connecting…", class `status-connecting`
  - `connected` → button "Disconnect" (enabled), status = `state.message` (falls back to "Connected"), class `status-connected`
  - `error` → button "Connect" (enabled — per spec.md user story 8, not stuck disabled), status = `state.message` (falls back to "Connection error"), class `status-error`
  - Also defines its own local `ConnectionStatus`/`CarProtocol`/`ConnectionState` types, deliberately **not** imported from `carConnection.ts` — see "Gotchas" below for why this was required, not a style choice.

- **`app/src/connectionUiState.test.ts`** — 7 `node:test` cases, one input/output pair per state (plus the two "message falls back to generic text" edge cases and one explicit check that the error-state button isn't disabled, directly covering spec.md user story 8). Same `node:test`/`node:assert/strict` style as tickets 02/03.

- **`app/src/renderer.ts`** — the renderer-world script, loaded by `index.html` via `<script type="module">`. On load: renders the default `disconnected` state (there's no initial-state query on `window.carAPI`, per ticket 03's gotcha 8, so this is the correct default — a fresh `CarConnection` always starts there). Wires the toggle button's `click` to call `window.carAPI.connect()` when current status is `disconnected`/`error`, or `window.carAPI.disconnect()` when `connected`/`connecting`, `.catch()`-logging any rejection (e.g. a stray click racing an in-flight state transition). Subscribes via `window.carAPI.onStatus(callback)` as the *only* source of truth for re-rendering — this is what satisfies "the UI reacts correctly to a status push at any time" (the automatic-drop-detection UI story), independent of whether the push was triggered by a user click or an unprompted event from main (e.g. the car dropping).

- **`app/public/index.html`** — replaced the ticket-01 placeholder with a single `<button id="toggle-button">` and `<span id="status-text">`, inline `<style>` for the four status-color classes (grey/amber/green/red for disconnected/connecting/connected/error) and a disabled-button style, and `<script type="module" src="../dist/renderer.js"></script>`.

## A real build problem found and fixed (not just a style choice)

The renderer needs the `ConnectionState` type. My first instinct was `import type { ConnectionState } from "./carConnection.ts"` in both `connectionUiState.ts` and `renderer.ts` — this type-checked fine, but **broke the actual `npm start` launch**: `dist/carConnection.js` came out as an ES module (`import { EventEmitter } from "node:events";` with no `require` wrapper), and Electron's main process crashed on load with `SyntaxError: Cannot use import statement outside a module`.

Root cause: the renderer files must compile to native ES modules (so `<script type="module">` can load them with zero Node access, per ADR-002 — Electron's renderer main world has no `require` when `nodeIntegration: false`), while `main.ts`/`preload.ts`/`carConnection.ts`/`carIpcHandlers.ts` must stay CommonJS (Electron's main/preload process loads them via `require()`). tsc compiles per-*program*, not per-file: even a type-only import still pulls the imported file into the same compilation unit, and tsc emits `.js` for every file in that unit. So compiling `renderer.ts`/`connectionUiState.ts` as ESM (needed) while they type-only-imported `carConnection.ts` caused tsc to also re-emit `dist/carConnection.js` as ESM, clobbering the CommonJS version `main.ts` needs — with `npm run build` running the renderer tsc pass second, the broken ESM version was what actually shipped.

**Fix:** `connectionUiState.ts` now declares its own local `ConnectionStatus`/`CarProtocol`/`ConnectionState` types (structurally identical to `carConnection.ts`'s, matched via TypeScript's structural typing rather than a shared nominal import) instead of importing them. `renderer.ts` imports `ConnectionState` from `connectionUiState.ts` (not `carConnection.ts`), keeping `carConnection.ts` entirely out of the renderer's compilation graph. Verified after the fix: `dist/carConnection.js` starts with `"use strict"` (CommonJS) and `dist/renderer.js`/`dist/connectionUiState.js` use `import`/`export` (ESM), and `npm start` launches without error.

Similarly, `renderer.ts` needed `window.carAPI`'s type but can't import it from `preload.ts` (same CommonJS-vs-ESM program problem) — so it locally re-declares a `CarApi` interface matching preload.ts's exactly, documented with a comment pointing at this same root cause.

**This is a real, documented drift risk**: if `carConnection.ts`'s `ConnectionState` shape or `preload.ts`'s `CarApi` shape ever changes, these two local re-declarations in `connectionUiState.ts`/`renderer.ts` must be updated by hand — nothing will fail to compile if they're not (structural typing means a superset/subset mismatch might silently still "work" for the fields renderer.ts happens to use, or fail with a type error only if a genuinely incompatible shape is passed). Flagging this for the review phase and any future ticket touching those two files.

## Build/tooling changes

- **`app/tsconfig.renderer.json`** (new) — extends the base config, overrides `"module": "ES2022"` (target/lib/outDir/rootDir inherited), `"include": ["src/connectionUiState.ts", "src/renderer.ts"]` only.
- **`app/tsconfig.build.json`** — `exclude` gained `"src/connectionUiState.ts"` and `"src/renderer.ts"` (previously only excluded test files), so the CommonJS main-process build pass doesn't also try to compile these two ESM-bound files.
- **`app/tsconfig.json`** (base, used by `npm run typecheck` and by `node:test`'s implicit type context) — `"lib"` gained `"DOM"` and `"DOM.Iterable"` alongside the existing `"ES2022"`, since `renderer.ts` is part of the base program too (needed for `document`/`HTMLButtonElement`/`window` types during `tsc --noEmit`). This is ambient-only; main-process files don't use any DOM globals, so this is a no-op for them.
- **`app/package.json`** — `"build"` script changed from `"tsc --project tsconfig.build.json"` to `"tsc --project tsconfig.build.json && tsc --project tsconfig.renderer.json"` — two passes, one CommonJS (main/preload/connection/IPC modules) and one ESM (renderer + its pure UI-state module), writing into the same `dist/` folder without conflict since they're disjoint file sets after the `tsconfig.build.json` exclude change above.
- `"typecheck"` and `"test"` scripts are unchanged — `tsc --noEmit` on the base config type-checks everything in one pass (mixed module settings don't matter for type-checking, only for emit), and `node --test src/**/*.test.ts` already globs up the new `connectionUiState.test.ts` automatically.

## Other gotchas / non-obvious decisions

1. **No initial-state query, so the default render is always `disconnected`** (per ticket 03 gotcha 8) — `renderer.ts` hardcodes this as its starting `currentState` rather than trying to derive it any other way. Correct because a freshly constructed `CarConnection` always starts there.
2. **`handleToggleClick`'s branch condition treats `connecting` the same as `connected`** (both call `disconnect()`) — this matches spec.md's "the button shows Connecting… and is disabled" story: since the button is disabled during `connecting`, this branch is normally unreachable via a real click, but it's still the semantically correct fallback for the (rare, documented) stray-click-race case ticket 03's notes called out, rather than leaving `connecting` unhandled.
3. **No error swallowing**: `window.carAPI.connect()/.disconnect()` rejections are `console.error`-logged, not silently dropped and not thrown further (there's no sensible synchronous catch point in a DOM event handler, and the next `onStatus` push already reflects the real outcome) — consistent with general.md's "do not swallow errors silently" while not over-engineering a retry/toast mechanism the ticket never asked for.
4. **`npm audit`'s 2 high-severity Electron 32.x advisories** (flagged in tickets 01/03) are unchanged by this ticket — still worth a look before a security-focused review round, not fixed here (would require a breaking Electron major bump, out of scope).
