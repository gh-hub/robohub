# 01 — [spec] HTTP:80 connections must detect drops without polling

**What to build:** When the car is connected via the HTTP:80 fallback protocol, the app must still detect when the connection goes away and automatically flip the UI out of "Connected" — the same guarantee the TCP:100 path already has via socket `close`/`error` listeners. The spec requires this unconditionally, not scoped to one protocol: "the UI never keeps claiming 'Connected' after the car has gone offline" (Solution section) and "I want the app to automatically detect when my connection drops... without me needing to notice on my own" (User Story 6).

Currently `carConnection.ts`'s `probeHttp()` is a one-shot GET that doesn't retain a socket (`this.socket` stays `null` after an http80 connect), so nothing is watching the connection after the initial probe succeeds — the UI will silently show "Connected" forever until the user manually disconnects.

Investigate what's actually possible against the HTTP:80 example firmware (check `docs/` for the firmware source referenced in earlier tickets) — e.g. a lightweight periodic liveness check (explicitly allowed here as an exception to "event-based, not polled," since polling was ruled out for the TCP path where a real event-based primitive exists, but no such primitive is available over one-shot HTTP), or keeping the underlying TCP connection open post-GET if the firmware supports it, or another concrete mechanism. Document whichever approach is chosen and why in this ticket and in `PROGRESS/notes/`. If no clean live-detection mechanism can be built against the http80 protocol at all, this must be explicitly documented as a known protocol limitation in spec.md's Further Notes (not just a code comment) and confirmed as acceptable — do not silently leave the gap.

**Blocked by:** None — can start immediately

**Status:** ready

- [x] Http80-connected sessions have some form of automatic drop detection (polling exception explicitly permitted here only if no event-based primitive exists over HTTP) that updates the UI to `disconnected`/`error` without requiring the user to click Disconnect first — implemented as a periodic liveness GET (`CarConnection.startHttpLivenessPolling()` in `app/src/carConnection.ts`), reusing the same side-effect-free `GET /` used for the initial http80 probe, every `CAR_HTTP_POLL_INTERVAL_MS` (5s, `app/src/carConfig.ts`). On a failed poll it transitions the state machine to `disconnected` (mirrors the TCP path's clean-close outcome, since a failed/timed-out GET is the only signal available — there's no way to distinguish a clean vs. abrupt drop over one-shot HTTP the way TCP's `close` vs `error` events do). The interval is cleared in `stopHttpLivenessPolling()`, called both when a poll detects the drop and from `disconnect()`, so no timer is ever left running past the session it belongs to.
- [x] The chosen mechanism (or the documented limitation, if no mechanism is feasible) is explained in a code comment and in the ticket/plan notes — see `CarConnection`'s class doc comment and `startHttpLivenessPolling()`/`checkHttpLiveness()` in `app/src/carConnection.ts`, and `PROGRESS/notes/implement-review-round-1-fix-01-http80-drop-detection.md`.
- [x] Automated test coverage added for the new drop-detection behavior on the http80 path (using the existing local mock HTTP server pattern from ticket 02's tests) — two new tests in `app/src/carConnection.test.ts`: "an http80 session detects a drop via periodic liveness polling and goes to disconnected" and "disconnect() on an http80 session stops the liveness poll (no leaked timer)".
- [x] N/A — a code fix was implemented (periodic liveness polling), not a documented limitation, so spec.md's Further Notes section did not need a new "accepted gap" entry. spec.md is unchanged by this ticket.
