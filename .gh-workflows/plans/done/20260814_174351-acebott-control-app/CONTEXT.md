# Context: acebott-control-app

## What we're building

An Electron desktop app (TypeScript, no framework) that connects to the ACEBOTT QD001 smart car over Wi-Fi/TCP and displays connection status with a single-button toggle UI.

## Key decisions

- Wi-Fi/TCP only, no Bluetooth — car firmware has zero BLE support — see [grill/ADR-001.md](grill/ADR-001.md)
- Main process owns the TCP socket; renderer uses IPC only — see [grill/ADR-002.md](grill/ADR-002.md)
- Car's actual protocol (TCP:100 binary vs HTTP:80) is NOT confirmed yet against real hardware — the `CarConnection` module (ticket 02) probes both automatically at runtime, but which one the physical QD001 actually speaks is still an open, user-deferred manual verification (see ticket 02's "Manual verification" section)
- Repository layout: app code lives in new `app/` subdirectory
- Wi-Fi network joining is manual (user joins `ESP32-Car` via macOS Wi-Fi menu); no programmatic switching
- Config values (IP `192.168.4.1`, SSID `ESP32-Car`, port TBD) are hardcoded constants; no settings UI needed yet
- Single toggle button ("Connect" / "Disconnect"), not two separate buttons
- Connection-drop detection is event-based (listen for socket `close`/`error`), not polled
- Dev-mode only (`npm start`); no signed `.app`/`.dmg` packaging for this ticket

## Gotchas

1. **Car protocol is unconfirmed against real hardware:** The `CarConnection` module probes both TCP:100 and HTTP:80 automatically, and the mock-server test suite proves that logic is internally consistent — but which protocol the physical QD001 car actually speaks has NOT been confirmed live. This is deliberately deferred to the user (see ticket 02's "Manual verification" section for a copy-pasteable script); do not treat it as done, and do not attempt to reach `192.168.4.1` or join `ESP32-Car` from an agent session.
2. **No Bluetooth in ACEBOTT firmware:** All ACEBOTT firmware examples use Wi-Fi/TCP only. Do not attempt to build or probe for BLE support; it doesn't exist.
3. **Repo root has no package.json/.gitignore/monorepo tooling:** `app/` is a fully self-contained npm project (own `package.json`, `tsconfig.json`, `.gitignore`). No root-level scripts wire into it.
4. **TS execution strategy:** production build compiles via `tsc --project tsconfig.build.json` to `app/dist/` before running (`npm start` = `npm run build && electron .`). Tests run raw TypeScript directly via Node's built-in type stripping (`npm test` = `node --test src/**/*.test.ts`, Node ≥22.6) — no ts-node/tsx dependency. Relative imports between `app/src/*.ts` files must use an explicit `.ts` extension (e.g. `from "./carConfig.ts"`); `tsconfig.json` has `rewriteRelativeImportExtensions: true` (TS ≥5.7) so `tsc` rewrites those to `.js` correctly in compiled output. `tsconfig.build.json` (extends the base config, excludes `src/**/*.test.ts`) keeps test files out of `dist/`; `npm run typecheck` still uses the base config so tests stay type-checked.
5. **`npm audit` flags 2 high-severity advisories** in the installed Electron 32.x line (upstream CVEs disclosed after that minor's release). Fixing requires a breaking major bump to Electron 43 — left as-is, not a runtime concern since the app doesn't do anything privileged yet. Worth a look before a later security-focused review.
6. **HTTP:80 sessions cannot hold a persistent connection open** (the example HTTP firmware closes its socket after every single request — see implement-02 notes gotcha 1), but as of round-1 fix 01 they DO have automatic drop detection via periodic liveness polling (`CarConnection.startHttpLivenessPolling()` in `app/src/carConnection.ts`, re-running the same side-effect-free `GET /` every `CAR_HTTP_POLL_INTERVAL_MS` = 5s). If the real car turns out to speak HTTP:80 rather than TCP:100, the UI will still correctly flip to a terminal state on a drop — just up to ~5s later than TCP:100's near-instant socket-close detection. **As of round-2 fix 01, a failed poll always routes to `error`, never `disconnected`** — a failed GET can't distinguish clean vs. abrupt drops the way TCP's `close`/`error` events do (no clean-disconnect signal exists over one-shot HTTP polling at all), so every poll failure is treated as an abrupt/unexpected drop. `disconnected` for an http80 session is still reachable, but only via the user's own manual "Disconnect" click (`CarConnection.disconnect()`), never via the poll path. See PROGRESS/notes/implement-review-round-1-fix-01-http80-drop-detection.md for the original polling rationale and PROGRESS/notes/implement-review-round-2-fix-01-http80-error-vs-disconnected.md for the error-vs-disconnected fix.
7. **[SUPERSEDED by round-1 fix 02 — kept for history] Preload scripts need `sandbox: false` in `webPreferences`, or local `require()`s inside them silently fail.** This was true when `preload.ts` had a runtime (value) `require("./ipcChannels.js")`. As of round-1 fix 02, `preload.ts` inlines its 3 IPC channel-name string constants instead of importing them, so it has zero local runtime imports, and `main.ts`'s `BrowserWindow` no longer sets `sandbox: false` (Electron's default sandbox is restored). **The underlying constraint still applies going forward**: any local **value** import/require added to `preload.ts` (as opposed to a type-only `import type`, which is erased at compile time and is always safe) will silently break `window.carAPI` again under the default sandbox — with the only trace being a console warning/`preload-error` event, never a thrown exception visible in the main-process terminal. See gotcha 13 and PROGRESS/notes/implement-review-round-1-fix-02-sandbox-false-review.md for the fix and how it was verified.
8. **`window.carAPI.connect()`/`.disconnect()` resolve once the action is *initiated*, not once it has settled** — they return `Promise<void>`, not the resulting `ConnectionState`. Render exclusively from `window.carAPI.onStatus(callback)`; there is no `getStatus()`/initial-state query, so assume `"disconnected"` until the first push (a fresh `CarConnection` always starts there). See implement-03 notes gotcha 1 for why (a naive "resolve with `getState()`" implementation returned a stale `"connected"` snapshot for disconnect, since `CarConnection.disconnect()` resolves before its socket's `close` event actually fires).
9. **Two tests in `carConnection.test.ts` (ticket 02's file) were fixed this session for a genuine, pre-existing race that intermittently hung the entire test suite** — not a regression from ticket 03's changes, but discovered while verifying ticket 03's suite is green. See implement-03 notes gotcha 3 for the full root-cause (a `state-change` listener registered too late, plus `resetAndDestroy()` racing the client's own `connect` event). No production code in `carConnection.ts` was changed, only two test assertions.
10. **`app/src/connectionUiState.ts` and `app/src/renderer.ts` must never import from `carConnection.ts` or `preload.ts` (even `import type`)** — those two files compile to CommonJS (Electron's Node-based main/preload loader needs `require()`), while `connectionUiState.ts`/`renderer.ts` compile to native ES modules (`tsconfig.renderer.json`) so `<script type="module">` can load them in the renderer with zero Node access, per ADR-002. tsc emits `.js` for every file in a compilation unit, even ones only reached via a type-only import — so importing `carConnection.ts`'s types from a file in the ESM build pass causes tsc to also re-emit `dist/carConnection.js` as broken ESM, crashing `main.ts` at launch (`SyntaxError: Cannot use import statement outside a module` — this actually happened and was fixed this session, see implement-04 notes). The fix in place: `connectionUiState.ts` and `renderer.ts` locally re-declare the `ConnectionState`/`CarApi` type shapes they need instead of importing them. **If either shape changes in `carConnection.ts`/`preload.ts`, these local copies must be updated by hand** — nothing will auto-detect the drift.
11. **`CarConnection`'s API surface grew two additive fields this session (round-1 fix 01), neither of which needed touching `main.ts`/`carIpcHandlers.ts`:** `CarConnectionOptions.httpPollIntervalMs` (optional override, defaults to the new `CAR_HTTP_POLL_INTERVAL_MS` = 5000 in `app/src/carConfig.ts`) and three new private methods (`startHttpLivenessPolling`/`checkHttpLiveness`/`stopHttpLivenessPolling`). Neither `ConnectionState` nor `ConnectionStatus` shapes changed, so gotcha 10's "locally re-declared type shapes" in `connectionUiState.ts`/`renderer.ts` do NOT need updating. If a future ticket exposes the poll interval as a constructor-visible knob elsewhere (e.g. a settings UI), remember `CarConnection` is instantiated once in `main.ts` with no options object currently — that's where an override would need to be threaded through.
12. **When adding a `setInterval`-based background mechanism to a long-lived class like `CarConnection`, do not `.unref()` it as a defensive default** — it was tried during round-1 fix 01 and broke `node --test`: an unref'd timer that is the only thing keeping the event loop alive gets treated as "no remaining work" by the test runner, which cancels the still-pending test promise instead of letting the timer fire. Since the poll timer is always explicitly cleared on every code path that ends the session (drop detected, manual disconnect), there's no real leak risk from leaving it ref'd. See PROGRESS/notes/implement-review-round-1-fix-01-http80-drop-detection.md gotcha 1 for the full explanation, and gotcha 2 there for a related test-hygiene fix (two pre-existing http80-connect tests needed an explicit `disconnect()` added so they don't leave a live poll running past test-file exit).
13. **`sandbox: false` is gone from `main.ts` as of round-1 fix 02 — `preload.ts` is now self-contained.** Its 3 IPC channel-name constants are inlined as local literals (kept in sync by hand with `ipcChannels.ts` — small enough surface that this is a deliberate, accepted duplication per general.md's "no over-engineering"). The remaining `import type { ConnectionState } from "./carConnection.ts"` stays safe because TypeScript erases type-only imports entirely at compile time — they never become a runtime `require()`, so they don't trip the sandboxed preload loader (this distinction — value import vs. type-only import — is the crux of the whole fix; see gotcha 7 above). Do not add a new local **value** import to `preload.ts` without re-verifying against the default sandbox (the throwaway `executeJavaScript`-probe technique in implement-review-round-1-fix-02-sandbox-false-review.md's "How it was verified" section is the reusable pattern for that).
